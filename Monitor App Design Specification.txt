MONITOR APP DESIGN SPECIFICATION

Product scope, architecture, platform constraints, and experience direction
Version 1.2
20 November 2026


DOCUMENT PURPOSE

This document defines the current scope and direction of Monitor App. It consolidates the user requirements, preferences, rejected ideas, assistant proposals, technical recommendations, and unresolved questions established in the design conversation.

The product is intended to be a self-hosted environment for monitoring, understanding, and selectively controlling a collection of personal computers, servers, mobile devices, network relationships, and self-hosted software. It should be useful as a practical diagnostic tool, but it should also be unusually enjoyable to observe and manipulate. The application may contain interaction that is deliberately elaborate or even functionally unnecessary when that interaction makes the system feel alive, tactile, and worth exploring.

The central experience combines two complementary ideas:

1. A living schematic that represents the whole computing environment and the relationships within it.
2. An exploded architecture that reveals the internal structure of a selected device or service.

These should be different scales of one continuous environment, not competing screens or unrelated visualization modes.

This document uses four status labels:

CONFIRMED USER DIRECTION
The user explicitly endorsed or required this direction. It should be treated as a product constraint unless the user changes it.

ASSISTANT PROPOSAL
This is a recommended implementation or design response. It is included to make the project actionable, but it has not been approved merely by appearing here.

OPEN EXPLORATION
The conversation did not settle the choice. Multiple options should remain visible until prototypes, technical tests, or further user direction justify a decision.

REJECTED OR DEPRIORITIZED
The user found the direction generic, boring, overwhelming, or otherwise unsuitable. It should not return as the primary concept without a materially different rationale.


AUTHORITATIVE ARCHITECTURE AMENDMENT

CONFIRMED USER DIRECTION

Monitor App is a decentralized peer-to-peer monitoring system. It must not require a Monitor App controller, central telemetry database, designated authority device, or always-on Monitor App host. Every supported computer or phone runs the same logical peer service and is capable of collecting its own state, retaining local data, connecting directly to paired peers, serving monitoring data, and presenting the experience appropriate to that platform.

The user is willing to add a device initially by its Tailscale IP address. After application-level pairing, two devices should reconnect directly whenever both devices have Tailscale reachability and the Monitor App service is running. Tailscale supplies private reachability only. A Tailscale IP address and tailnet membership are not Monitor App identity or authorization.

The first personal-scale topology may use explicit pairwise trust. Each paired peer retains the other peer's application identity and reconnect information. A central discovery, enrollment, telemetry, history, or authorization service is not required. No peer becomes the global source of truth merely because it accepted the initial pairing.

Telemetry and history are origin-owned. A peer is authoritative for records it produced. Other peers may cache and replicate those immutable or versioned records with explicit origin, sequence, source time, quality, and freshness. Pairwise synchronization should converge after disconnection without requiring global consensus for origin-owned streams. Conflicting administrative metadata requires an explicit conflict rule rather than last-writer ambiguity.

The monitored environment also includes observed devices and components that cannot run a Monitor App peer service, such as a UPS or audio interface attached to a computer. A host peer acts as a collection gateway through a purpose-built adapter selected case by case. Possible mechanisms include USB or HID, NUT, SNMP, operating-system audio APIs, vendor APIs or SDKs, and serial protocols; no specific mechanism or model is confirmed merely by appearing in this list. Observed devices retain stable identities and history independent of the peer currently collecting them. The domain model distinguishes peer identity, observed-device identity, physical or logical attachment, collection source, adapter capability, adapter health, and data freshness. Purpose-built inspectors remain required; peripherals must not be flattened into generic metric cards.

Multiple Monitor App peers may operate on the same physical LAN, exchange observations, and monitor managed switches and network topology. The physical LAN is a separate domain from the Tailscale overlay. The model includes typed switches, ports, peers, peripherals, VLANs, uplinks, physical attachment, overlay reachability, and reported or inferred topology relationships. Managed-switch collection is adapter-specific and may use SNMP, REST, vendor APIs, SSH, LLDP, forwarding databases, or another supported mechanism. Every observation preserves source, evidence, quality, and freshness, and the interface must distinguish device-reported topology from Monitor App inference.

Observations from multiple peers must reconcile around a strong observed-device identity such as a serial number, stable chassis identifier, or chassis MAC when available; an IP address alone is not sufficient identity. The initial implementation avoids redundant switch polling through explicit configured collector ownership. Switch and adapter credentials remain local to the provisioned collector peer and do not replicate automatically. Collection failover occurs only after another peer has been explicitly provisioned with the required adapter, permissions, and credentials.

The breadth-of-observation goal is that anything which can be measured safely and truthfully should be measurable. Monitor App therefore uses a capability-driven, extensible metric and observation registry rather than a permanently narrow allowlist. Adapter output may include numeric values, counters, discrete state, events, inventory and configuration facts, errors, and topology evidence. Every observation preserves entity, source, source time, unit when applicable, quality, freshness, and collection cost. Unsupported, permission-denied, stale, unknown, error, and unavailable are explicit states and must never be represented as zero.

Breadth does not mean indiscriminate collection or unlimited retention. Sampling and retention adapt to collection cost, change rate, device power, local storage, and replication budgets. Peers may retain high-resolution raw detail locally while replicating bounded summaries or requested ranges. Secrets, content payloads, and unrelated packet, file, or message contents remain excluded by default. Sensitive or high-cost categories require explicit opt-in and remain visible in collection and retention settings.

Network observation is limited to aggregate operational measurement without communication identities or content. Allowed measurements include bandwidth and throughput, negotiated or link speed, interface or switch-port utilization, aggregate byte and packet totals, aggregate errors, drops, discards, retries, queue health, latency and reachability probes, and historical aggregate trends. Monitor App must not capture packets, headers, or payloads; retain individual packet records; record flows, sessions, connections, sockets, source or destination identities, DNS or query history; inspect per-application or per-process traffic; classify content; or use deep packet inspection. Mirroring or promiscuous collection for those prohibited purposes is not allowed. Adapter registration and review must reject prohibited network observations before collection begins.

Useful automated defensive threat detection is allowed as a separate, explicitly enabled security capability with common-sense, legal, and privacy guardrails. Baseline detection may use aggregate operational measurements, device identity and authentication failures, unexpected peer, configuration, or link changes, unusual utilization, and summarized alerts already produced by an IDS, firewall, switch, or operating system. Monitor App should prefer consuming alert summaries over raw traffic. It does not by default intercept payloads, obtain decryption credentials, attempt exploits, scan indiscriminately, or monitor networks the user does not own or have authorization to monitor. Any deeper flow-derived or packet-derived security module requires explicit enablement, clear disclosure, local processing, bounded retention, separate permission, and an additional design and security review. Findings carry evidence and confidence and must not claim compromise without supporting evidence.

Breadth also requires strong categorization and modularity. Capability modules use versioned, namespaced contracts that declare entity types, observations, relationships, sampling and retention metadata, categories, and inspector descriptors. A canonical observation catalog classifies signals by domain, entity, subsystem, source, unit, temporal behavior, importance, privacy, and collection cost. The living schematic summarizes relationships and state; domain lenses such as power, audio, storage, network infrastructure, and thermal condition reveal coherent subsets; search reaches exact signals. Unknown compatible modules receive a truthful generated fallback inspector, while important integrations retain purpose-built inspectors. Users may enable or disable modules, adjust retention, and pin or hide designed content, but do not build a blank dashboard. The domain model remains the source of truth.

This amendment supersedes every earlier controller-centric or mandatory self-hosted-Headscale statement in this document, including prior CONFIRMED USER DIRECTION recorded from an incomplete brief. Those statements remain in the historical text only where their superseded status is useful to explain the project record. The living schematic, exploded architecture, game-like interaction, historical time travel, purpose-built UI, platform targets, functionality-first delivery, and meaningful-test requirements remain unchanged.


AUTHORITATIVE PRODUCT-SCOPE AMENDMENT

CONFIRMED USER DIRECTION

Monitor App is not limited to live computer telemetry. It is also a personal inventory, planning, and decision-support environment for the physical and digital systems the user owns, operates, is designing, or is considering buying. The scope includes equipment, components, software, services, rooms and installation locations, racks and enclosures, cables and connectors, power and signal paths, projects, candidate products, and retailer offers.

The product must make a clear, persistent distinction between actual state and design state. Actual state describes objects the user has, their possession and location, installed connections, and evidence about what is running now or ran historically. Design state describes proposed objects, candidate products, hypothetical relationships, requirements, alternatives, and scenario-specific calculations. A plan may reference existing actual objects, but a proposed object or connection never becomes owned, installed, connected, or running without an explicit transition that preserves its planning history. The interface, queries, totals, warnings, automation, and historical replay must identify which state they use.

One universal object model should connect these domains without pretending that every object has the same capabilities. A monitored peer, a passive loudspeaker, a rack shelf, a cable, a room, a planned component, and a candidate product may share identity, naming, provenance, lifecycle, relationships, history, and attachments while retaining type-specific specifications, constraints, observations, and inspectors.

The living schematic, exploded architecture, and historical replay remain the primary experience. They should eventually project both operational reality and user-authored plans from the same domain model. The interface must distinguish observed facts, imported specifications, user-entered facts, calculations, assumptions, recommendations, and unknown values. Planned state must never be displayed as live telemetry, and a product listing must never become an owned device merely because it was considered.

Physical-system planning is in scope. Monitor App should be able to represent and evaluate audio signal chains, RF coordination and propagation constraints, electrical loads and circuit budgets, thermal generation and cooling paths, physical dimensions and clearances, mounting, connector and cable compatibility, and other domain-specific constraints. These are distinct modules over shared objects and relationships, not one generic compatibility score.

Cable inventory and planning are a first-class part of this scope. The user's earlier work system paired connector/category codes with reusable length codes for fast entry. Monitor App should preserve the speed of that combinatorial workflow while replacing static sheets with structured connector-end, length, rating, condition, location, custody, and connection data. Reusable templates and quick manual selection are the primary workflow; specialized scanning hardware and QR codes are not required.

Product sourcing and price tracking are in scope. Candidate products and specific offers should preserve manufacturer identity, model or variant, seller, region and currency, price and availability history, source time, source URL or provider, shipping and tax information when available, and source quality. The system may alert on price, availability, or suitability conditions, but it must expose stale, incomplete, incomparable, or restricted source data rather than inventing certainty.

Customizable alerts and automation are core scope. The intended model is event plus condition plus action, covering examples such as peer disconnection, storage pressure, service failure, equipment availability, a candidate price falling below a threshold, a cable leaving its assigned location, or a project becoming build-ready. Push notifications to an Android companion and platform notifications are desired actions. The deterministic rule engine must operate without requiring the UI or an AI model, preserve evaluation and action history, use deduplication and cooldowns, and keep read-only observation separate from permissioned operational control.

Distributed local AI is in scope as an optional assistance layer. Lightweight models or deterministic tools may run on individual peers, while more capable local models may run on peers with suitable resources. Routing should consider capability, privacy, availability, latency, energy, and user policy. AI may explain, search, compare, propose plans, translate natural language into inspectable draft rules, or call approved read-only tools. It is not an authority source, identity provider, replication owner, or automation runtime, and it may not execute material actions without the same explicit permissions and confirmations required of any other caller.

This scope does not change the delivery priority. The executable equal-peer foundation, truthful object identity and provenance, local persistence and query, platform behavior, historical reconstruction, and a plain usable client precede sourcing automation, local-AI orchestration, or advanced visual production. Bounded design studies may continue, but they do not count as implemented functionality or displace prerequisite work.


1. EXECUTIVE SUMMARY

CONFIRMED USER DIRECTION

Monitor App must not become another generic monitoring dashboard. Conventional collections of rectangular cards, interchangeable charts, progressive information-density screens, and infinitely customizable workspaces fail to provide the desired identity.

The living schematic and exploded architecture concepts are both strong and should be treated as complements. The living schematic explains how devices, services, storage, synchronization, and network paths relate across the environment. The exploded architecture reveals what is inside the selected object. Moving between them should feel like traveling through one coherent system.

The product may be pointlessly interactive in a positive sense. It can behave like a technical toy, a game interface, a miniature world, an interactive sculpture, or something interesting to watch without a task. The interface may contain magnetic motion, physical response, animated traffic, elaborate transitions, idle behavior, and other details whose purpose is enjoyment rather than efficiency.

Historical time travel is a valuable feature regardless of the final visual style. The user should be able to select an earlier moment, see the environment as it existed then, replay changes, compare past and present, and investigate how an incident developed.

Data movement is also a feature that should survive changes in visual style. Transfers, synchronization, backups, and network traffic should be represented as relationships and activity within the chosen environment rather than defining the entire visual identity by themselves.

The application should be purpose-built before it is customizable. Device types, integrations, diagnostics, and controls should receive thoughtfully designed interfaces. The user should be able to choose what matters and tune behavior, but should not be required to construct the application from a blank canvas.

The setup objective is download, install, and pair. The user may enter a peer's Tailscale IP address for initial contact. Pairing must establish a Monitor App identity independent of network membership, after which peers reconnect automatically whenever both services are running. Monitor App must not expose a public monitoring port or require an always-on application controller.

ASSISTANT PROPOSAL

The working architecture should consist of:

- One equal Monitor App peer service per supported computer or phone.
- Local collection and a local SQLite history store on each peer.
- Direct authenticated peer sessions addressed initially by Tailscale IP.
- Pairwise identity verification and pinned peer keys independent of tailnet membership.
- Origin-owned telemetry streams with durable per-peer replication cursors.
- Local read APIs and platform-appropriate experience clients on every peer.
- Platform-specific collection on Android where mobile restrictions permit it.
- Observed devices and components collected through purpose-built gateway adapters on a host peer.
- Stable observed-device identity and typed attachment and collection relationships.
- A physical-LAN model distinct from Tailscale overlay reachability, including managed switches, ports, VLANs, uplinks, and evidence-qualified topology.
- Explicit collector ownership for network and peripheral adapters, with credentials retained only on provisioned peers.
- An inventory and relationship model assembled from local state and replicated peer records.
- Purpose-built integration adapters, beginning with the most valuable systems such as Syncthing.

Tailscale should supply private reachability. Monitor App should not attempt to operate Tailscale or require Headscale. Monitor App telemetry, history synchronization, queries, and future authorized actions use application protocols directly between paired peers over the private network.

The development process should separate technical foundation from visual convergence. Enrollment, telemetry, history, and the underlying object model can advance while several genuinely different visual concepts are prototyped in parallel. This respects the user's instruction to explore broadly before narrowing.


2. PRODUCT DEFINITION

Monitor App is a self-hosted application for observing, understanding, and selectively managing a personal computing environment. The environment can contain:

- Desktop and laptop computers.
- Home servers and small hosted servers.
- Android phones, tablets, or other supported Android devices.
- Storage devices and filesystems.
- Network interfaces, private-network routes, and connectivity paths.
- Self-hosted applications and background services.
- Synchronization systems such as Syncthing.
- Containers or other workload groups when a supported integration exists.
- Backup systems and replication relationships when a supported integration exists.
- Physical equipment, components, accessories, cables, connectors, spaces, racks, and installation positions.
- Named projects and design scenarios containing proposed objects, relationships, requirements, and alternatives.
- Product definitions, variants, seller offers, and price or availability observations kept separate from actual instances.

The product has two equally legitimate forms of use.

Practical use answers questions quickly:

- Is everything healthy now?
- Which device or service is unavailable?
- Is the information current or stale?
- What changed?
- What else depends on the failed component?
- Where is data moving?
- Why is synchronization slow or incomplete?
- What happened at a particular time?
- What safe action can be taken?

Exploratory use allows the user to:

- Watch the environment while it is operating normally.
- Follow paths and activity without a specific diagnostic objective.
- Pull devices apart visually.
- Rotate, open, isolate, or examine components.
- Trigger harmless visual reactions.
- Rewind and replay recorded system behavior.
- Treat the environment as a technical sculpture, toy, or miniature world.

The practical form establishes the reliability and clarity floor. The exploratory form creates the product's identity.


3. PRODUCT GOALS

CONFIRMED USER DIRECTION

- Create a distinctive experience rather than a standard dashboard with a visual theme.
- Combine a whole-environment schematic with detailed exploded views.
- Permit rich and game-like interaction that does not need a narrow productivity justification.
- Preserve historical state and make time a navigable dimension.
- Favor strong, curated, purpose-built interfaces over infinite user composition.
- Allow selective customization where it improves relevance.
- Make installation and secure pairing automatic enough to feel like a consumer application.
- Require no Monitor App controller or central monitoring database.
- Allow manual peer bootstrap by Tailscale IP followed by automatic direct reconnection.
- Keep Tailscale reachability separate from Monitor App identity and authorization.
- Include non-peer devices through stable observed identities and purpose-built host adapters.
- Keep actual/owned/running state visibly and structurally separate from design scenarios while allowing intentional comparison and assignment.
- Include connector-and-length-centered cable inventory and planning without requiring QR codes or dedicated scanner hardware.
- Include modular physical, audio, RF, electrical, and thermal design constraints.
- Include candidate sourcing, price history, customizable automation and notifications, and optional distributed local AI as later functional layers.
- Explore a wide breadth of concepts before choosing one visual direction.

ASSISTANT PROPOSAL

- Make the environment understandable without training or a separate topology manual.
- Give devices and services stable identities and locations so the user develops spatial memory.
- Treat freshness, uncertainty, and missing data as visible states.
- Make failures appear in dependency context rather than as unrelated alerts.
- Give every important metric an exact textual reading in addition to its visual representation.
- Provide a fast route and a scenic route to the same information.
- Default to read-only monitoring and add real controls through a separate permission model.
- Keep routine operation independent of any vendor-operated monitoring cloud.


4. NON GOALS

REJECTED OR DEPRIORITIZED

Monitor App is not intended to be:

- A generic business-intelligence dashboard builder.
- A blank workspace into which users drag, resize, and configure arbitrary widgets.
- A collection of interchangeable rectangular cards.
- An ordinary network topology graph with animated lines added for decoration.
- A fake physical instrument panel filled with gauges.
- An infrastructure atlas whose regions are the main visual idea.
- A simple focus-and-periphery interface presented as the defining concept.
- A literal simulation of every packet, file, process, or hardware component.
- A replacement for enterprise-scale observability, packet capture, security-event management, or fleet administration in the initial scope.
- A game in which playful gestures can accidentally execute real administrative commands.
- A cloud service that requires the user's monitoring history to leave the self-hosted environment.

The product may borrow useful mechanics from rejected concepts. For example, an inspector can focus on one object, and a network view can use topology. Those mechanics should support the stronger vision rather than become the product's primary identity.


5. PRIMARY EXPERIENCE MODEL

5.1 THE LIVING SCHEMATIC

CONFIRMED USER DIRECTION

The living schematic is one of the strongest concepts. It should represent the computing environment as a carefully designed system of objects and meaningful connections.

ASSISTANT PROPOSAL

The schematic should differ from an unconstrained force-directed graph. It should use deliberate layout rules, stable placement, functional regions when useful, and recognizable object identities. The user should be able to learn where things live.

The schematic may contain:

- Devices as recognizable objects rather than identical nodes.
- Services nested within or visibly associated with their host devices.
- Storage attached to the devices or services that use it.
- Typed connections for hosting, dependency, synchronization, routing, backup, or data movement.
- Direction and broad intensity of active traffic.
- Availability, freshness, and reliability history.
- Shared-cause failure grouping.
- Event markers and historical changes.
- Visual lenses for connectivity, storage, synchronization, power, or service health.

The positions of objects should not constantly rearrange themselves. Automatic layout may establish or repair a scene, but stable spatial memory is more valuable than a mathematically optimal graph at every moment.

Healthy operation should remain visually alive but calm. An unhealthy object should become noticeable through a controlled combination of position, contrast, motion, connection behavior, and explanation. The entire scene should not turn red because one service has a warning.

5.2 THE EXPLODED ARCHITECTURE

CONFIRMED USER DIRECTION

The exploded architecture complements the living schematic. A selected device or service should reveal its internal layers and constituent parts.

ASSISTANT PROPOSAL

A server may separate into:

- Physical or virtual hardware identity.
- Processing and memory.
- Storage devices, filesystems, and capacity.
- Network interfaces and private-network connectivity.
- Operating-system state.
- Processes or workload groups.
- Hosted services.
- Service-specific integrations.

A laptop may emphasize:

- Battery and charging behavior.
- Estimated remaining runtime.
- Power draw.
- Thermal condition.
- Wireless connectivity.
- Storage.
- Important applications or background services.

An Android device may emphasize:

- Battery condition.
- Charging state.
- Network type.
- Reachability.
- Data freshness.
- VPN or private-network state.
- Signals available within Android's permission and background-execution limits.

The internal structure should be capability-driven. The domain model should not invent components that a peer, adapter, or evidence-qualified inference cannot support.

The exploded transition can be elaborate. Layers may separate magnetically, unfold, rotate, illuminate, or expose internal paths. The structure should remain stable enough that repeated inspection builds familiarity.

5.3 ONE ENVIRONMENT AT THREE SCALES

CONFIRMED USER DIRECTION

The living schematic and exploded architecture should be understood as complements rather than alternatives.

ASSISTANT PROPOSAL

The primary hierarchy should be:

Ecosystem scale
The user sees devices, major services, dependencies, routes, activity, and incidents across the environment.

Device scale
The selected computer, server, phone, or logical host opens into hardware, operating-system, storage, network, and hosted-service layers.

Service scale
The selected service opens into its own specialized model. Syncthing, for example, reveals peers, folders, transfer direction, completion, errors, and recent activity.

Moving between these scales should use semantic zoom. Zooming in reveals structure and changes the type of information shown. It should not merely enlarge the same object and labels.

Selection, historical time, active visual lens, comparison state, and breadcrumbs should survive movement between scales.


6. GAME-LIKE AND GRATUITOUS INTERACTION

CONFIRMED USER DIRECTION

The application is allowed to be pointlessly interactive. It may behave almost like a game or something that is simply enjoyable to watch and manipulate.

This does not mean that the application should become unnecessarily complicated. It means the product may be visually and physically elaborate while remaining functionally understandable.

ASSISTANT PROPOSAL

6.1 MAGNETIC COMPONENTS

Objects can react to the pointer or touch. A dragged device can pull its relationships with it. Connections can stretch, bend, vibrate, and settle. Components can snap back into a stable arrangement.

6.2 DISASSEMBLY AND REASSEMBLY

The user can pull apart a device, rotate a layer, temporarily isolate a service, or inspect a network subsystem as a physical object. Releasing an object may cause it to reassemble smoothly.

This manipulation is inspection only. Pulling a service out of a visual model must never stop the service.

6.3 REACTIVE INFORMATION

Connections can pulse when real activity occurs. Storage can visibly fill. A synchronization event can move through the devices involved. A reconnect can trigger a designed startup sequence.

These animations should represent real direction, timing, and broad intensity. They should not pretend to show individual packets or files unless the underlying integration actually provides that detail.

6.4 CINEMATIC CAMERA MOVEMENT

Selecting an object can move the camera toward it, orbit it, enter it, or follow one of its connections. Investigating a remote service can become a visual journey through its host and network path.

The user must be able to bypass cinematic travel through search, keyboard navigation, a reduced-motion setting, or an immediate-open command.

6.5 AMBIENT PERSONALITY

The environment can contain idle motion, small visual reactions, transitions, and details that communicate no essential information. This is acceptable when those details remain quieter than operational activity and do not obscure status.

6.6 INTERACTIVE WORLD MODELS

OPEN EXPLORATION

Several levels of game-like presentation remain possible:

Interactive technical sculpture
The system resembles a precise mechanical or electronic object in a museum. The pleasure comes from unfolding, rotating, illuminating, and examining it.

Miniature computing world
Devices and services become structures, buildings, rooms, machines, roads, or transportation systems. The pleasure comes from watching a small world driven by real systems.

Science-fiction operating environment
The interface uses layered depth, dimensional navigation, elaborate controls, and cinematic presentation. The pleasure comes from operating something that feels technically advanced.

Digital organism
Devices, services, and connections behave like organs, tissues, nerves, or vessels. The pleasure comes from watching an environment that appears alive and changes organically with system behavior.

Precision schematic
The environment remains explicitly diagrammatic and engineering-oriented, but receives enough movement, depth, and physical response to become an interactive artifact rather than a static graph.

Architectural cutaway
Devices behave like spaces or constructed objects whose internal systems are exposed as walls, layers, and subsystems separate.

No single visual world has been selected. They should be explored in parallel rather than serially producing minor variations on one dashboard.

6.7 SAFE PLAY

ASSISTANT PROPOSAL

- Harmless manipulation must remain separate from real controls.
- No real action should begin from a decorative gesture.
- Operational controls should be labeled and visually distinct.
- Material actions should preview their exact target and likely effect.
- Historical playback must never replay commands against live devices.
- A global reduced-motion mode should disable nonessential movement.
- No essential fact should depend only on color, motion, or sound.
- Dense environments should aggregate activity rather than create hundreds of simultaneous effects.


7. HISTORICAL TIME TRAVEL

CONFIRMED USER DIRECTION

Historical time travel is a strong feature independent of the final visual implementation.

The user should be able to revisit a previous state of the whole environment rather than opening a disconnected metrics page.

ASSISTANT PROPOSAL

7.1 CORE CAPABILITIES

- A global time scrubber.
- A persistent and obvious return-to-now control.
- Event markers for disconnects, restarts, alerts, transfers, configuration changes, and user actions.
- Playback of recorded system changes through the living environment.
- Selection of a specific date and time.
- Then-versus-now comparison.
- Comparison between two historical moments.
- Per-object history that respects the globally selected time.
- A detailed multitrack timeline when deeper investigation is needed.
- Incident bookmarks that preserve a useful surrounding time range.

7.2 CONSISTENT HISTORICAL STATE

When historical time is active, visible devices, components, relationships, metrics, alerts, and events should resolve to the same logical instant whenever recorded data exists.

The application should distinguish:

- A recorded value.
- A rolled-up value.
- A derived value.
- An interpolated display value.
- Missing data.
- Data that had not yet arrived at the selected time.

Discrete states such as online status, action results, and service restarts should not be interpolated.

7.3 STORAGE MODEL

ASSISTANT PROPOSAL

Use three complementary forms of history:

Metric samples
Timestamped values such as CPU usage, battery level, throughput, storage activity, and latency.

Events
Discrete occurrences such as connect, disconnect, restart, warning, action, configuration change, or completed transfer.

Snapshots
Periodic compact representations of the environment's state. Historical reconstruction can begin at the nearest snapshot and apply later events and metrics.

This hybrid approach should make seeking fast without storing a complete copy of the environment every second.

7.4 RETENTION

OPEN EXPLORATION

Exact sampling and retention periods are unresolved. A likely design is:

- Recent high-resolution metrics.
- Lower-resolution rollups for longer periods.
- Longer retention for sparse events and action records.
- User-pinned incidents protected from ordinary deletion.
- A visible storage budget and retention policy.

Retention defaults should be based on realistic observation-volume tests, peer storage and power constraints, and raw-versus-summary replication budgets.


8. PURPOSE-BUILT INFORMATION DESIGN

CONFIRMED USER DIRECTION

The application should be opinionated about how information is presented and flexible about which information matters to the user.

Battery health, synchronization, network paths, storage, and service health should not all become interchangeable cards. Each subject deserves a presentation designed around its own questions and relationships.

ASSISTANT PROPOSAL

8.1 GLOBAL EXPERIENCE AREAS

Environment
The living schematic and ambient home view.

Inspector
A purpose-built detailed view for the current device, component, service, or relationship. It expands from the selected object and retains parent context.

History
Global time control, replay, event alignment, and comparison. History changes the temporal state of the same environment rather than becoming a separate product.

Search and command
Immediate access to devices, services, metrics, settings, and permitted actions. This is the fast path around cinematic navigation.

Setup and administration
Peer pairing, capability modules, adapters, collector ownership, retention, replication budgets, updates, access policy, and peer backups. This can use a more conventional utility layout because its purpose is configuration rather than the primary monitoring experience.

8.2 SPECIALIZED INSPECTORS

Laptop inspector

- Charge state.
- Charge and discharge history.
- Power draw.
- Estimated runtime with confidence.
- Battery health where supported.
- Thermals.
- Wireless quality.
- Storage and important services.

Server inspector

- Processing and memory pressure.
- Storage capacity and activity.
- Network interfaces.
- Hosted services and containers where supported.
- Service dependencies.
- Backup and replication state.
- Current incidents.

Android inspector

- Battery and charging.
- Reachability.
- Connection type.
- VPN state.
- Last successful collection.
- Signals available within Android permissions.
- Explicit indication when background restrictions make information stale.

Syncthing inspector

- Devices and peer relationships.
- Shared folders.
- Which folders exist on which devices.
- Transfer direction.
- Completion.
- Transfer rate.
- Bottlenecks.
- Connection type.
- Errors and recent synchronization events.

The Syncthing experience should resemble a synchronization fabric across the environment rather than a stack of independent progress bars.

Network-path inspector

- Direct or relayed connection.
- Endpoint reachability.
- Current and historical latency.
- Relevant routes.
- Interface changes.
- Path changes and reconnect events.

Storage inspector

- Devices and filesystems.
- Proportional allocation.
- Free space.
- Read and write activity.
- Replication and backup relationships.
- Drive health where supported.


9. CUSTOMIZATION PHILOSOPHY

CONFIRMED USER DIRECTION

The correct approach is a mix of hard-coded and user-customizable design. Infinite customization is overwhelming and weakens the potential of purpose-built solutions.

The application should already be capable and coherent before the user configures anything.

ASSISTANT PROPOSAL

9.1 CONTENT CUSTOMIZATION

High customization.

The user may choose:

- Which devices and services matter.

11. DOWNLOAD INSTALL AND PEER PAIRING

CONFIRMED USER DIRECTION

The desired setup is download, install, enter a peer's Tailscale IP, and pair directly. There is no Monitor App controller, mandatory Headscale deployment, or always-on Monitor App host. After successful pairing, the two services reconnect whenever both are running and reachable through Tailscale.

Tailscale configuration is outside Monitor App's authority in the initial scope. The user accepts entering a Tailscale IP address. Monitor App must not expose its peer port to the public Internet by default.

ASSISTANT PROPOSAL

11.1 DIRECT PAIRING FLOW

1. The user installs the same signed Monitor App peer package on two devices.
2. Each peer generates and protects its own application identity key.
3. On one device, the user chooses Add Peer and enters the other device's Tailscale IP and peer port.
4. The contacted peer displays or accepts a short-lived pairing approval.
5. Both peers prove possession of their application identity keys and bind the approval to both identities and the current handshake.
6. The user verifies a short authentication string, QR representation, or equivalent identity confirmation on both devices.
7. Each peer stores the other peer's stable application identity, approved address, capabilities, and trust state.
8. The peers exchange protocol compatibility and replication cursors.
9. Each peer begins serving its locally owned telemetry and synchronizing permitted cached history.
10. After interruption, either peer retries the stored Tailscale endpoint with bounded backoff and reauthenticates with a fresh challenge.

11.2 PAIRING AND IDENTITY RULES

- A Tailscale IP is a bootstrap address, not device identity.
- Tailnet membership alone grants no Monitor App access.
- Pairing approval is short lived and bound to both peer identities.
- Long-term trust is pinned to application public keys retained locally on each peer.
- Private keys never leave their originating device.
- Reconnection proves the pinned key with a fresh, replay-resistant challenge.
- Address changes require an authenticated update or explicit user repair; they must not silently replace identity.
- Unpairing removes local trust and replication permission. Revocation propagation across other pairwise relationships is explicit future work, not implied global authority.

11.3 RECONNECTION AND AVAILABILITY

- Both peers may initiate or accept a session; duplicate simultaneous sessions resolve deterministically to one logical relationship.
- Sessions use application TLS or an equivalently authenticated secure channel even inside Tailscale.
- A listener binds only to explicitly configured private interfaces or Tailscale addresses by default.
- Failure states distinguish service stopped, Tailscale path unavailable, authentication failure, protocol incompatibility, stale replicated data, and collector failure.
- Cached data remains visible with its origin and last synchronization time when a peer is offline.

11.4 OBSERVED DEVICE AND NETWORK ADAPTER SETUP

An observed UPS, audio interface, managed switch, or other non-peer device is added through a purpose-built adapter on a selected collector peer. Setup records a stable observed-device identity, adapter type, collection capability, attachment or topology relationship, and health/freshness evidence. Credentials remain on the selected collector peer. Another peer does not begin polling the device merely because it learned that the device exists.

For managed network equipment, the user explicitly assigns collector ownership. Failover requires provisioning another peer with the adapter and credentials. Reconciliation uses a serial, chassis identifier, chassis MAC, or another strong identity when supported; an IP address alone cannot merge records.

11.5 PLATFORM-SPECIFIC LIMITS

OPEN EXPLORATION

The project must determine how peer listening, protected key storage, background execution, firewall rules, and Tailscale-address binding work on each platform. Android may reconnect and collect only while permitted by its lifecycle and background-execution policy. The product must display this limitation as freshness rather than imply continuous service.


12. PROPOSED DECENTRALIZED SYSTEM ARCHITECTURE

ASSISTANT PROPOSAL

12.1 EQUAL PEER SERVICE

Every supported computer or phone runs one logical Monitor App peer with these responsibilities:

- Generate and protect its application identity.
- Collect local signals and adapter observations.
- Retain its own telemetry and selected replicas in a local database.
- Listen on an explicitly configured Tailscale-facing endpoint.
- Initiate direct sessions to configured peers.
- Authenticate pairwise trust independently of Tailscale.
- Synchronize origin-owned records and replication cursors.
- Serve local inventory, current state, and bounded history.
- Host or support the platform-appropriate experience client.

There is no controller role. A peer may have more storage, remain online longer, or be configured to retain more replicas, but that does not grant global authority.

12.2 LOCAL EXPERIENCE AND API

The experience client communicates with its local peer service and may render local or replicated state. The local API:

- Serves inventory, relationships, freshness, current state, and retained history.
- Streams local changes and synchronization progress.
- Exposes peer pairing and repair operations.
- Identifies which records are local, replicated, stale, incomplete, or unavailable.
- Never treats the visual scene as the source of truth.

12.3 PEER PAIRING AND DIRECTORY

Each peer stores a local directory containing approved peer identities, pinned public keys, configured Tailscale endpoints, capabilities, protocol compatibility, and per-peer trust state. Pairing is a bilateral operation. The directory is not a global membership authority, and trust does not automatically become transitive.

The initial implementation may require explicit pairwise pairing for each relationship. Later peer introductions must preserve explicit owner approval and must not turn one compromised peer into authority over the mesh.

12.4 ORIGIN-OWNED OBSERVATION LOG

Each peer owns an append-only or versioned sequence for records it produces. A record includes:

- Origin peer and origin sequence.
- Observed entity and component identity.
- Adapter and collection source.
- Source and ingestion times.
- Unit, quality, freshness, and collection cost.
- Numeric value, counter, state, event, fact, error, or topology evidence.
- Schema and capability identifiers.

Only the origin advances its stream. This avoids distributed write consensus for telemetry. Another peer validates, stores, acknowledges, and requests missing ranges but does not rewrite the origin record.

12.5 REPLICATION

Pairwise sessions exchange durable cursors and bounded batches. Replication should:

- Resume after either peer or network path restarts.
- Accept byte-identical retries idempotently.
- Reject conflicting content at an accepted origin sequence.
- Detect gaps and request bounded missing ranges.
- Apply backpressure and local storage budgets.
- Preserve raw local detail while permitting lower-cost replicated summaries.
- Expose partial history and last synchronization time truthfully.
- Avoid deleting the only retained copy of origin data merely because another peer acknowledged it.

Origin telemetry needs no global consensus. Shared annotations, display metadata, retention pins, or future actions require separately specified merge and authorization semantics.

12.6 OBSERVED DEVICES AND COMPONENTS

Peer-capable nodes and observed devices are different entity types. A UPS, audio interface, switch, sensor, service, or other component may be observed through an adapter on a host peer without running Monitor App itself.

The observed entity retains a stable identity independent of attachment host. Typed relationships include attached-to, collected-by, hosted-on, connected-to-port, member-of-VLAN, uplink-to, and reachable-over-overlay. Adapter observations preserve source and evidence so a view can distinguish a device report, operating-system report, neighbor protocol, forwarding database evidence, and Monitor App inference.

12.7 PHYSICAL LAN AND TAILSCALE OVERLAY

The physical network and Tailscale overlay are separate but related models. Physical topology may include managed switches, ports, VLANs, trunks, uplinks, peers, peripherals, and inferred attachments. Tailscale represents private overlay reachability between peer services. An overlay session must not be displayed as proof of a particular physical path.

Multiple peers may observe the same LAN object. Reconciliation uses strong identity and evidence, not IP address alone. Explicit collector ownership prevents redundant polling initially. Adapter credentials remain local to provisioned collectors, and failover is enabled only through explicit provisioning.

12.8 ADAPTER AND CAPABILITY REGISTRY

Adapters declare:

- A versioned, namespaced module identity and compatibility range.
- Supported entity and observation types.
- Typed relationships and their evidence semantics.
- Discovery and stable-identity evidence.
- Required permissions and local credentials.
- Expected collection cost and safe sampling bounds.
- Sampling and retention metadata.
- Domain, subsystem, importance, privacy, and cost categories.
- Quality, error, and freshness behavior.
- Purpose-built inspector descriptors and a truthful generated fallback schema.

The registry is extensible enough to measure new supported facts without weakening privacy or allowing unbounded unsafe collection. Registration permits aggregate network operations data but rejects packet detail, communication identities, session histories, per-process inspection, and content classification. Adapter failure is isolated and visible. The canonical observation catalog, rather than a screen or adapter-specific dictionary, is the source for search, domain lenses, retention, replication summaries, and inspector fallback behavior.

12.9 LOCAL PERSISTENCE

Every peer uses a versioned local store for identity, peer directory, origin records, retained replicas, replication cursors, adapter state, topology evidence, and audit events. SQLite WAL remains the accepted personal-scale starting point. Storage and retention policies operate per peer and distinguish locally irreplaceable origin data from replaceable replicas.

12.10 COMMUNICATION MODEL

- Peers connect directly over Tailscale endpoints entered during pairing.
- Peers may initiate and accept sessions; no public endpoint is enabled by default.
- Application authentication and encryption remain required inside Tailscale.
- Live and historical synchronization use resumable, bounded, sequence-aware messages.
- Duplicate simultaneous sessions resolve deterministically.
- Protocol compatibility is negotiated explicitly.
- Direct versus relayed Tailscale transport is reachability evidence, not Monitor App identity.

12.11 ACTION SAFETY

Future actions target the peer or adapter that owns the capability. They remain outside the replication authority of ordinary telemetry. Requests include actor, target, authorization, expiration, idempotency, and a scope preview. A replicated historical record can never cause a live action.

12.12 DEPLOYMENT MODEL

The first deployment unit is a native peer service plus a platform-appropriate local experience. Windows, Fedora, and Ubuntu use managed background services. Android uses only operating-system-supported background mechanisms and must report when the peer is not continuously available. There is no controller appliance or Compose deployment requirement.


13. DATA MODEL

ASSISTANT PROPOSAL

Environment
One locally assembled view of the paired monitoring mesh. Important fields include identity, name, time zone, local retention policy, replication budget, and visual preferences.

Node
A peer-capable computer or phone. Important fields include stable application identity, platform, role, configured Tailscale endpoint, capabilities, freshness, and lifecycle state.

Observed device
A stable physical or logical entity that may not run Monitor App, such as a UPS, audio interface, managed switch, service, or sensor. Important fields include strong identity evidence, type, adapter, current collector ownership, capabilities, freshness, and attachment history.

Component
A nested part of a node or service. Important fields include type, parent, health, capabilities, and specialized view adapter.

Relationship
A typed connection between two objects. Important fields include source, target, type, direction, validity interval, evidence source, reported-or-inferred status, quality, and confidence. Physical-LAN and Tailscale-overlay relationships remain distinguishable.

Capability module
A versioned namespaced contract declaring entity types, observations, relationships, collection metadata, categories, compatibility, and inspector descriptors.

Observation definition
A canonical catalog entry classifying a signal by domain, entity, subsystem, source, unit, temporal behavior, importance, privacy, and collection cost.

Metric series
Origin-sequenced numeric or categorical observations. Important fields include entity, origin peer, adapter source, source time, unit, collection policy, quality, freshness, cost, and retention tier.

Event
A discrete occurrence. Important fields include time, type, object, severity, evidence, and correlation keys.

Snapshot
A compact representation of state at a point in time. Important fields include time, schema version, object state, and reconstruction cursor.

Incident
A group of related symptoms and evidence. Important fields include affected objects, possible cause, evidence, status, and annotations.

Action
A requested control operation and result. Important fields include actor, target, preview, authorization, timestamps, result, and audit information.

Peer pairing
A time-bounded bilateral trust transaction. Important fields include both peer identities, bootstrap Tailscale endpoint, short-lived approval, key fingerprints, expiration, transcript binding, and completion state.

Replication cursor
The durable per-origin sequence through which a receiving peer has validated and retained records, including any known gaps and summary fidelity.

Collector assignment
The explicit peer and adapter authorized to collect an observed device. Important fields include observed-device identity, owning peer, adapter capability, credential location reference, health, and optional explicitly provisioned failover.

13.1 STORAGE ENGINE

OPEN EXPLORATION

Each peer uses file-backed SQLite in WAL mode for the personal-scale foundation. The schema must distinguish irreplaceable local origin data from replicated data that can be reacquired, and must retain durable peer and per-origin cursors. A future storage change requires a benchmark using expected device and observation count, sampling frequency, replication load, historical seek behavior, backup, and restore.

13.2 BACKUP AND RESTORE

Backups should include:

- Local peer identity and protected recovery metadata.
- Paired-peer directory and trust decisions.
- History schema.
- Local origin records and retained replicas within the selected policy.
- Observed-device identity, inventory, relationships, collector assignments, and topology evidence.
- Capability-module configuration and explicit sensitive-category choices.
- Encryption metadata required for recovery.

Restore must be tested per peer as part of release acceptance. Restoring one peer must not duplicate its origin identity or fork its sequence without an explicit recovery rule. A backup that has never been restored is not sufficient evidence of recoverability.

15. SECURITY PRIVACY AND CONTROL SAFETY

ASSISTANT PROPOSAL

15.1 SECURITY REQUIREMENTS

- Use short-lived, transcript-bound bilateral pairing approval.
- Pin application peer identity independently of a Tailscale IP address.
- Use TLS for Monitor App protocols even inside the private network.
- Protect peer identity keys, local databases, and adapter credentials at rest.
- Separate read, configure, and control permissions.
- Default new peers and adapters to read-only access.
- Run collectors with least privilege.
- Record security-relevant changes and actions.
- Sign installers and updates.
- Verify update signatures before execution.
- Support peer unpairing, device revocation, and key rotation without a central authority assumption.
- Do not send telemetry or usage analytics to third parties by default.
- Encrypt peer backups that contain sensitive history or credentials.
- Keep adapter and managed-device credentials local to explicitly provisioned collector peers.
- Permit aggregate operational network measurements but prohibit packet detail, communication identity and session history, per-process inspection, DNS/query history, and content classification.

15.2 CONTROL SAFETY

Inspection and control must remain visually and behaviorally separate.

Pulling apart a device, moving a service, replaying history, or following a connection is non-operational.

A real action should begin only through a labeled control that shows:

- The exact target.
- The requested operation.
- Required permission.
- Likely effect.
- Affected dependents when known.
- Whether the action is reversible.

Material actions should require confirmation. Actions should expire if not executed promptly. A delayed device must not unexpectedly execute an old command after reconnecting.

Historical mode should disable live actions or require an explicit return to the present before an action can be sent.

15.3 PRIVACY CONTROLS

- List the categories collected from each device.
- Show the retention applied to each category.
- Allow sensitive collectors to be disabled.
- Avoid collecting file names, process arguments, or secret values unless a selected feature specifically requires them.
- Allow diagnostic exports to be reviewed and redacted before sharing.
- Distinguish Monitor App telemetry from Tailscale reachability metadata.
- List which records are local origin data, replicated raw data, replicated summaries, or inference.
- Make sensitive or high-cost capability modules explicit opt-in with visible collection and retention behavior.


16. PERFORMANCE RESILIENCE AND ACCESSIBILITY

ASSISTANT PROPOSAL

16.1 PERFORMANCE PRINCIPLES

The application should become useful before every visual effect and detail has loaded. It should present cached state quickly, reconnect in the background, and progressively add current detail.

Suggested initial targets, subject to reference-hardware testing:

- Warm desktop launch displays usable cached state within two seconds.
- Selection feedback begins within 100 milliseconds.
- Live updates apply incrementally instead of rebuilding the whole scene.
- Historical seeking begins from indexed snapshots.
- The renderer aggregates distant or dense activity.
- Effects degrade before navigation, input, or exact diagnostics become slow.
- Hidden or background scenes reduce or pause animation.
- Mobile collection adapts to battery and operating-system limits.

16.2 RESILIENCE

The product should distinguish:

- Local peer service unavailable.
- Remote peer service unavailable.
- Tailscale path unavailable.
- Peer authentication or protocol incompatibility.
- Device sleeping.
- Telemetry stale.
- Replication delayed, partial, summarized, or storage-limited.
- Assigned collector unavailable.
- Observed device unavailable or moved to another attachment host.
- Integration failed.
- Monitored service failed.

Every peer should show cached state with explicit origin, source time, and last synchronization time. A peer buffers its origin telemetry and bounded replicas. A nonessential adapter failure should not prevent the peer service from starting in a degraded read-only state.

Schema migration, backup, restore, and rolling version compatibility should be tested.

16.3 ACCESSIBILITY

An elaborate spatial interface requires a complete semantic model.

- Every device, component, relationship, and state needs a text name.
- Keyboard navigation should follow the environment hierarchy.
- A structured outline should provide access to the same objects and actions as the scene.
- Focus, selection, and severity must not depend on color alone.
- Reduced motion should disable camera travel, parallax, oscillation, and nonessential physics.
- Charts should expose exact values, units, time ranges, and textual summaries.
- Touch targets and text must remain usable on mobile.
- Essential information must remain available when advanced rendering is disabled.

20. ACCEPTANCE CRITERIA

ASSISTANT PROPOSAL

Enrollment
Two supported devices can move from signed downloads and a manually entered Tailscale IP to verified bilateral pairing. They reconnect whenever both services run, and failure can be diagnosed, retried, repaired, unpaired, or rolled back without a controller.

Environment
The application presents stable device and service identities, typed relationships, freshness, and incidents without relying on a grid of generic cards.

Semantic zoom
The user can move from ecosystem to device to service while preserving selection, time, and context. Search reaches the same destination directly.

Specialized inspectors
The first release contains distinct information designs for its selected device types and integrations rather than one universal widget template.

Historical state
The user can select a prior time, replay an interval, compare with the present, and identify missing or rolled-up data.

Safe play
Visual manipulation cannot execute a real command. Real actions use explicit authorization and appear in history.

Self-hosting
Monitoring, history, identity, and queries operate on peers without a vendor monitoring backend or always-on Monitor App host. Tailscale supplies reachability only. Peer backup and restore are tested without duplicating origin identity.

Resilience
Cached state, stale data, sleeping devices, peer-service outage, Tailscale path failure, replication delay, collector outage, observed-device outage, and monitored-service failure are distinguished.

Performance
The agreed reference environment remains responsive under the agreed device and event load. Effects degrade before input and diagnostics.

Accessibility
Keyboard access, structured navigation, text equivalents, exact values, and reduced motion cover essential information and actions.

Actual and design state
The current view, historical actual view, named design scenario, and comparison overlay are unmistakable. Design-only objects and relationships never appear as owned, installed, connected, or running. Promotion to actual state is explicit and retains plan and decision history.

Cable inventory and planning
The user can describe both connector ends, direction, nominal or measured length, units, ratings, condition, location, and actual or planned connection through fast manual templates. The system can find available actual cables for a planned connection and explain mismatches without QR codes or scanner hardware.

Physical constraints
Audio, RF, electrical, thermal, cable, dimensional, and mounting findings show rule/version, inputs, units, provenance, assumptions, confidence, and unknowns. Missing data cannot produce an unqualified compatible or safe result.

Sourcing
Product, variant, offer, and actual instance remain distinct. Price and availability observations preserve seller, region, currency, source time, quality, and failure/staleness state.

Automation and notifications
A durable rule survives restart, evaluates exactly once under equal-peer ownership, records why it fired, observes cooldown/deduplication, and retries notification delivery without converting notification permission into control permission.

Local AI
The product remains useful without AI. When enabled, a bounded job runs only on an eligible peer, uses granted tools, labels actual versus design context, cites sources/provenance where practical, and cannot overwrite authoritative facts or bypass action confirmation.


21. RISKS AND MITIGATIONS

Spectacle hides meaning

Risk:
Motion and visual density can make diagnosis harder.

Mitigation:
Keep exact factual panels, use clear hierarchy, test practical tasks, and distinguish decorative from operational motion.

Purpose-built integrations expand scope

Risk:
Specialized views require more work than generic cards.

Mitigation:
Define an adapter contract, begin with a narrow integration set, and require a clear user job for each new inspector.

Setup cannot be completely automatic

Risk:
Privilege prompts, app stores, signing, licensing, and alternate-server configuration differ by platform.

Mitigation:
Build platform-specific orchestration, state unavoidable prompts clearly, and test clean-machine installation.

Pairwise trust becomes difficult to repair

Risk:
A lost key, changed Tailscale address, restored backup, or compromised peer can make pairwise trust ambiguous.

Mitigation:
Pin trust to application keys, bind address changes to authenticated identity or explicit repair, test unpairing and rotation, and prevent backup restore from silently forking one peer identity.

Replicated history grows without bound

Risk:
High-resolution observations and replicas can consume every peer's local storage.

Mitigation:
Use adaptive collection, per-peer retention tiers, replication budgets, visible summaries, and different treatment for irreplaceable origin data and replaceable replicas.

Android data becomes stale

Risk:
Background restrictions can interrupt collection.

Mitigation:
Expose freshness, use operating-system-supported patterns, and avoid unsupported promises.

Collector compromise exposes local credentials

Risk:
A peer assigned to collect a managed switch or peripheral may hold sensitive adapter credentials.

Mitigation:
Keep credentials local, use least privilege, do not replicate them, make collector ownership explicit, and require explicit credential provisioning for failover.

Conflicting topology evidence misidentifies devices

Risk:
Multiple peers may observe the same switch, port, or peripheral differently, and IP-based merging can combine unrelated devices.

Mitigation:
Use strong identity evidence, preserve each source and confidence, distinguish reported from inferred topology, and surface unresolved conflicts.

Security detection overstates evidence or invades privacy

Risk:
Automated threat detection can create unsupported compromise claims or expand into traffic surveillance.

Mitigation:
Keep it explicitly enabled and separately permissioned, prefer summarized alerts and aggregate signals, process locally with bounded retention, require evidence and confidence, and prohibit default payload interception, decryption credentials, exploit attempts, indiscriminate scanning, or unauthorized-network monitoring.

Controls increase consequences

Risk:
A compromised peer or mistaken action could affect real systems.

Mitigation:
Launch read-only first, separate permissions, use previews and expiration, and audit every action.

Broad exploration never converges

Risk:
Many prototypes can consume time without helping the user decide.

Mitigation:
Use common data, bounded prototypes, common tasks, and a predeclared evaluation rubric.

Advanced rendering consumes excessive power

Risk:
Ambient use may monopolize a GPU or drain batteries.

Mitigation:
Set frame and effect budgets, aggregate activity, pause unseen effects, and provide low-power modes.

Actual and design state become confused

Risk:
A proposed device, connection, cable, cost, or load could be mistaken for installed or running reality.

Mitigation:
Use separate scoped assertions, named scenarios, explicit overlays, separate totals, and an audited plan-to-actual transition.

External product data is stale or misleading

Risk:
Retailer access may fail, offers may not be comparable, and specifications may be incomplete or wrong.

Mitigation:
Separate products from offers, retain source and time, expose stale/unavailable/incomparable states, use permitted adapters, and require exact evidence for suitability findings.

Equal peers duplicate automation

Risk:
Replicated events or ownership changes could send duplicate notifications or repeat actions.

Mitigation:
Define durable execution ownership, idempotency, outbox state, reassignment rules, and two-peer failure tests before enabling live delivery.

AI overreaches or hallucinates

Risk:
A model may confuse actual and design state, follow malicious retrieved text, invent facts, or propose unsafe actions.

Mitigation:
Keep AI optional and permission scoped, validate tools outside the model, store outputs as derived artifacts, expose sources, and keep deterministic services authoritative.

OPEN EXPLORATION

Primary visual world

Options include technical sculpture, miniature world, science-fiction environment, digital organism, precision schematic, and architectural cutaway. Evidence should come from side-by-side prototypes using the same tasks.

Rendering technology

Options may include a WebGPU-based stack, native GPU UI, a game-oriented renderer, or a hybrid application shell. The decision requires tests of performance, text quality, accessibility, power use, and packaging.

Launch platforms

The project must decide whether to begin with Windows and Linux, whether Android ships with the first release, and when macOS becomes a supported target.

Peer service packaging

Choose and test native service installation, protected key storage, Tailscale-interface binding, firewall scope, upgrade, rollback, and uninstall for Windows, Fedora, Ubuntu, and Android's permitted lifecycle.

Replication and retention defaults

Choose raw-versus-summary replication, storage budgets, origin-data protection, gap recovery, and retention after measuring realistic observation volume and historical seek needs.

Retention defaults

Choose after measuring realistic data volume on expected self-hosted hardware.

Local user and peer administration authentication

Choose how a local user authorizes pairing, adapter credentials, sensitive modules, threat detection, and future actions. Peer application identity is separately pinned through bilateral proof. Offline recovery and multi-device key rotation matter.

Action scope

Choose between a read-only first release, a few safe actions, or broader administration after a security review and concrete use-case selection.

Remote notification transport

The notification capability is confirmed. Transport options include local-only notifications, an Android companion, a self-hosted push bridge, or optional third-party channels. Privacy and reliability require a separate decision.

Actual/design persistence shape

Choose between scoped assertions in one store, versioned scenario overlays, or another representation after testing promotion, comparison, shared actual objects, and plan revision history. The separation itself is confirmed.

Cable taxonomy and quick entry

Choose the canonical connector taxonomy, reversible/directional rules, unit and tolerance defaults, counted-batch versus serialized-item threshold, and optional label/import format. Manual templates must remain sufficient; QR and dedicated scanners are not required.

Automation ownership and rule conflicts

Choose how an equal-peer mesh assigns one durable evaluator/outbox owner, transfers ownership after outage, and reconciles rule edits without duplicate effects.

Local AI runtime and routing

Choose supported model families, runtimes, hardware/resource budgets, context and embedding storage, tool policy, and task routing. Whole-job routing to one eligible peer is the initial proposal, not a confirmed implementation choice.

Peer directory propagation

The initial model permits explicit pairwise setup. Any future introductions or directory synchronization must preserve owner approval and avoid transitive trust escalation.

Shared metadata conflicts

Origin telemetry is single-writer, but annotations, display names, incident pins, topology corrections, and retention protection may be edited on multiple peers. Define merge and conflict semantics before replication.

Defensive threat detection depth

Baseline aggregate and summarized-alert detection is allowed when explicitly enabled. Any deeper flow-derived or packet-derived capability requires a separate design, permission, disclosure, retention, and legal/privacy review.

Sound

The game-like environment could benefit from subtle sound, but sound was not discussed as a requirement. If explored, it should remain optional and subordinate to visual and textual status.

Multi-user support

The initial architecture should not accidentally prevent future roles, but full multi-user tenancy is not established as an initial requirement.

25. GLOSSARY

Peer
The equal Monitor App service on a supported computer or phone. It owns an application identity, collects local signals, stores local and replicated records, connects directly to paired peers, and serves a local experience and API.

Observed device
A physical or logical device, service, or component that does not run a peer service and is measured through an adapter on a collector peer.

Collector ownership
The explicit assignment authorizing one peer and adapter to collect an observed device. Credentials remain local and failover requires separate provisioning.

Capability module
A versioned, namespaced declaration of entity types, observations, relationships, collection metadata, categories, compatibility, and inspector descriptors.

Observation catalog
The canonical classification of signals by domain, entity, subsystem, source, unit, temporal behavior, importance, privacy, and collection cost.

Component
A part of a device or service represented inside an exploded view.

Control plane
The Tailscale coordination layer that supplies overlay reachability. It is outside Monitor App identity, telemetry, history, and authorization.

Data plane
Direct authenticated application traffic carrying pairing, replication, queries, and future authorized actions between Monitor App peers.

Exploded architecture
A layered visual representation that reveals the internal structure of a selected device or service.

Origin stream
The ordered observation sequence written only by the peer that produced it and replicated without rewriting by other peers.

Replication cursor
The durable per-origin position and known-gap state retained by a receiving peer.

Inspector
A purpose-built detailed view for a device, service, component, or relationship.

Living schematic
The stable, animated model of devices, services, and relationships across the environment.

Semantic zoom
Navigation in which moving closer reveals internal structure and changes the information shown.

Snapshot
A compact saved state used with later events and metrics to reconstruct a historical scene.

Tailnet
The private Tailscale network used to make peer endpoints reachable. Tailnet membership alone grants no Monitor App trust.

Visual lens
A designed emphasis layer that highlights connectivity, storage, power, synchronization, service health, or another concern without rebuilding the environment.

Actual state
Externally real or possessed objects, actual locations and relationships, and observed current or historical operation. Possession, installation, connection, and running state are separate facts.

Design state
Objects, relationships, requirements, alternatives, assumptions, and calculations scoped to a named project or scenario revision. Design state is never implied actual state.

Cable specification
The typed description of two connector ends, directionality, length, ratings, supported signals/protocols, and physical/environmental properties shared by one or more cable items.

Product offer
A seller-specific, time-stamped price and availability observation for a product or variant. It is not the canonical product or an actual owned instance.

Automation rule
A versioned event-condition-action definition with durable schedule/evaluation state, ownership, idempotency, cooldown, and audit.

AI capability
An optional peer-advertised model/runtime and tool boundary describing eligible tasks, resources, privacy, availability, and limits.

27. UNIVERSAL INVENTORY ACTUAL STATE AND DESIGN STATE

CONFIRMED USER DIRECTION

The inventory is broader than a discovered-device list. It contains things the user possesses, operates, has installed, has ordered, plans to install, is comparing, or has retired. It also contains non-product objects needed to explain a system, including spaces, positions, circuits, thermal zones, signal paths, projects, requirements, and retailer offers.

Actual state and design state are separate but linkable planes:

- Actual state contains possessed or externally real objects, installed and observed relationships, present and historical operational state, physical location, custody, condition, and evidence.
- Design state belongs to a named scenario or project revision and contains proposed objects, placements, relationships, requirements, alternatives, assumptions, and calculated outcomes.
- A design may reuse an actual object without making every proposed relationship actual.
- Selecting or ordering a candidate and receiving or installing an item are explicit events. They create or link an actual instance while retaining the candidate, offer, decision, and plan history.
- The default current view must not mix design-only quantities, costs, loads, cable requirements, or connections into actual totals. An intentional overlay or comparison labels both sides.

ASSISTANT PROPOSAL

Use a small shared object envelope with typed capability extensions rather than a giant nullable record or unrelated databases. Shared fields should include stable object identity, object type and subtype, display name, actual-versus-design scope, project/scenario when applicable, possession and deployment states, provenance, validity interval, source references, attachments, tags, notes, and revision history. Type-specific modules own their specifications, observations, constraints, and inspectors.

Important object families include peers and services; observed devices and components; equipment, accessories, consumables, cables, connectors, mounts, racks, rooms, zones, and positions; projects, requirements, alternatives, decisions, tasks, and build states; canonical product models and variants; seller-specific offers; and actual instances.

Important relationship families include contains, installed-in, attached-to, connected-to, powered-by, sends-signal-to, cools, heats, blocks, depends-on, satisfies, candidate-for, offered-as, replaces, and derived-from. Every relationship should carry direction, validity, source, evidence, confidence, and actual-versus-design scope.

Identity rules are domain specific. A manufacturer model number identifies a product definition, not a unique owned unit. A seller URL identifies an offer, not the product across all sellers. A serial number may identify a physical instance. A user-authored planned object needs a stable local identity even before a product is selected.


28. CABLE CONNECTOR AND LENGTH SYSTEM

CONFIRMED USER DIRECTION

The cable system should recreate and improve the user's fast work-oriented cable coding method inside Monitor App, with primary emphasis on the relationship between the two connector ends, length, and additional cable parameters.

The reference system groups connector codes into Display, USB, Power, Audio, Network, and Miscellaneous sheets and pairs them with reusable length sheets containing common length buckets. This separation is useful: a quick-entry workflow can compose connector or cable-type input with length input without requiring a unique entry for every combination. Monitor App should retain that speed while making the resulting record exact, searchable, and editable.

ASSISTANT PROPOSAL

Model a cable as an actual serialized item or a counted batch, plus a cable specification. Each cable has two connector-end records. An end should be able to describe connector family and exact standard, form factor, plug/socket or gender where applicable, signal role or direction, orientation or keying, pin/pole count, locking mechanism, supported signal and protocol, version/category, and whether an adapter or active conversion occurs. Symmetric cables remain reversible; directional, conversion, optical, active, and power-delivery cables preserve source and destination roles.

Length is a unit-bearing property, not only a code. Preserve nominal manufacturer length, measured length, measurement time and method, tolerance, routed or required path length, slack allowance, and minimum bend radius where relevant. Common scan tokens such as 1 m, 2 m, 3 m, 4 m, 5 m, 6 m, 8 m, 9/10 m, and 12 m may remain configurable shortcuts rather than hard-coded product limits.

Additional parameters may include conductor count and gauge, shielding, impedance, category, bandwidth or data rate, supported protocols, maximum voltage/current/power, Power Delivery profile, active/passive construction, optical/electrical medium, jacket and fire rating, environmental rating, color, manufacturer/model, serial or lot, purchase source and cost, condition, test status and results, repair history, owner/custodian, storage bin, current endpoint connections, reservation, project assignment, and notes or photos. Unsupported and unknown values remain distinct.

Each physical cable should receive a stable Monitor App identity and an optional human-readable short label. The identifier should not encode every mutable property. Keyboard, touch, search, favorites, recent values, and connector-pair and length shortcuts should make entry fast without dedicated hardware. Bulk workflows should support rapid add, duplicate-and-adjust, location/custody change, check-in/out, and cycle counts. Phone-camera, QR, and dedicated scanner workflows are outside the required cable path.

Search and planning should answer questions such as which actual cables match two connector requirements and a minimum routed length, which are free versus connected or reserved, which planned connections lack a suitable actual cable, whether a directional cable is reversed, and whether length, bend radius, power, bandwidth, impedance, category, or environmental rating violates a constraint. An explicit plan-to-actual assignment links the planned cable requirement to a selected physical cable without erasing either record.

OPEN EXPLORATION

The exact legacy connector codes, optional printable label format, and migration mapping are unresolved. Import should be user-reviewed and preserve the original code as an alias; the application must not infer exact connector semantics from an ambiguous legacy code. QR codes and dedicated scanning hardware are not requirements.


29. PHYSICAL DESIGN AND ENGINEERING CONSTRAINTS

CONFIRMED USER DIRECTION

Monitor App should help design and validate real installations. It should combine inventory, topology, specifications, measurements, and planned relationships to surface incompatible, overloaded, undersized, overheated, or otherwise risky designs before assembly and during operation.

ASSISTANT PROPOSAL

Constraint modules should emit structured findings rather than one opaque score. Each finding identifies affected objects and relationships, the rule and version used, inputs and units, source and age, assumptions, confidence, severity, suggested remedy, and whether the check is measured, calculated, simulated, or unresolved.

Audio examples include connector and signal-type compatibility, balanced versus unbalanced paths, analog or digital format, sample-rate and clocking constraints, channel count, gain staging, amplifier and loudspeaker compatibility, impedance and load, cable length, latency, and acoustic placement assumptions.

RF examples include frequency ranges, legal region, channel plans, antenna characteristics, cable and connector loss, transmit-power limits, receiver sensitivity, occupied bandwidth, intermodulation and coexistence, line of sight, obstacles, placement, and measured versus modeled coverage. Regulatory or safety claims require jurisdiction and source version.

Electrical examples include nominal voltage and frequency, AC versus DC, phase and polarity, connector and conductor ratings, circuit and UPS budgets, peak and continuous load, inrush, power factor where known, grounding, protection devices, battery capacity, runtime assumptions, redundancy, and derating. Monitor App is decision support, not a substitute for a licensed professional or code inspection.

Thermal and physical examples include heat output, ambient range, airflow direction, cooling capacity, rack units, dimensions, weight, center of mass, mounting points, service clearance, cable routing, obstruction, noise, ingress, and location constraints. Unknown values should block confident approval rather than default to safe.


30. PRODUCT SOURCING PRICE AND AVAILABILITY

CONFIRMED USER DIRECTION

Monitor App should help find equipment that satisfies project requirements, retain candidate comparisons, record price and availability history, and notify the user when a configured buying condition becomes true.

ASSISTANT PROPOSAL

Keep product definitions separate from offers. A product definition holds manufacturer, family, model, variant, specifications, lifecycle, and source evidence. An offer holds seller, region, currency, condition, seller SKU, price, shipping, tax when available, stock state, URL, observed time, and source quality. Price comparisons normalize currency and included items only when conversion time and assumptions are visible.

Source adapters may use official APIs, feeds, permitted page retrieval, or user-entered records. They must respect credentials, provider terms, rate limits, robots and access restrictions, and source-specific freshness. A failed or blocked retrieval becomes stale or unavailable; it never becomes out of stock or zero price.

Suitability search should begin from explicit requirements and constraint findings. Ranking and AI summaries may assist, but exact specifications, exclusions, provenance, and unresolved compatibility remain visible. Affiliate or sponsored influence, if ever present, must be disclosed and must not silently change ranking.


31. AUTOMATION ALERTS AND NOTIFICATIONS

CONFIRMED USER DIRECTION

Users should be able to create customizable interactions for disconnections, prices, availability, measured thresholds, service state, inventory movement, project readiness, and other supported events or observations. Push notifications are an intended action.

ASSISTANT PROPOSAL

Rules use a versioned event-condition-action representation. Triggers may be event based, scheduled, threshold based, duration based, inventory-change based, or relationship aware. Conditions may reference actual or design state, current or historical observations, source freshness, project requirements, inventory availability, and dependency context. Actions may record an event, create or update an incident, notify, request acknowledgement, or propose a separately authorized operational action.

The rule engine runs as ordinary deterministic peer functionality, not inside the UI or an AI model. It persists schedules and evaluation state, supports debounce, cooldown, deduplication, escalation, quiet hours, retry, expiration, and idempotency, and records the input facts, rule version, decision, action attempt, and result. Relationship-aware grouping should suppress cascades such as many downstream disconnect alerts caused by one upstream failure.

Natural language may create a draft structured rule, but the user reviews the exact trigger, conditions, state plane, targets, data freshness requirements, actions, permissions, and notification destinations before activation. Historical simulation should show how a rule would have behaved without dispatching live actions.

OPEN EXPLORATION

Remote delivery may use an Android companion, a self-hosted push bridge, or optional third-party channels. Reliability, background restrictions, metadata exposure, credentials, acknowledgement, and offline behavior must be designed and tested before selecting a default.


32. DISTRIBUTED LOCAL AI

CONFIRMED USER DIRECTION

AI assistance should be local-first and able to use the resources of multiple Monitor App peers rather than assuming one cloud model or one permanently powerful machine.

ASSISTANT PROPOSAL

Publish AI capability as an optional peer capability describing model identity and version, supported tasks and tools, context and output limits, hardware and memory needs, latency, energy policy, availability, privacy class, and whether work stays local. A router selects an eligible execution peer under user policy and fails transparently when none is available.

AI tools should query the same typed object, observation, history, constraint, sourcing, and rule APIs used by non-AI clients. Tool calls carry the requesting identity and permission scope. Outputs cite the objects, records, sources, times, calculations, and rule versions they relied on where practical. Generated facts and recommendations are stored as derived artifacts with model provenance, never silently written over observed or user-confirmed facts.

Initial useful tasks include semantic search, incident explanation, comparison summaries, missing-information detection, planning alternatives, documentation assistance, and draft automation rules. Deterministic code remains responsible for identity, trust, persistence, replication, exact constraint calculations, rule evaluation, notifications, and actions.

OPEN EXPLORATION

Model families, runtimes, embedding stores, distributed inference versus job routing, context replication, hardware acceleration, and model acquisition are unresolved. The first implementation should prefer routing whole bounded jobs to one eligible peer rather than assuming cross-peer tensor execution.


33. IMPLEMENTATION STATUS AND CLAIM BOUNDARY

The repository currently implements a tested controller-era monitoring foundation plus the first peer-native libraries: generated pairing/session/replication contracts, bilateral P-256 proof and compatibility logic, and a versioned file-backed SQLite WAL peer store for identity/trust, origin records, cursors, observed-device evidence, adapters, and collector assignments. The peer network service, local API, platform key-store integration, durable replay storage, and two-peer convergence path remain unimplemented. The controller-era components are migration inputs, not a supported equal-peer release.

The equal-peer service, universal inventory and object model, actual/design-state split, cable inventory and quick-entry workflow, living schematic, exploded architecture, historical scene replay, physical-design constraint modules, RF coordination, audio/electrical/thermal planning, product sourcing, price tracking, automation engine, push notification delivery, and distributed local-AI routing are planned and not implemented in the current repository unless later change-log and executable test evidence says otherwise.

Documentation examples describe intended behavior and do not establish retailer access, product compatibility, regulatory compliance, platform support, continuous Android background operation, notification delivery, AI correctness, or permission to control a device.
