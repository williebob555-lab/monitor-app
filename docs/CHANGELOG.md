### Changed

- The client is now a mobile command center on one shared UI: views and styles moved from `MonitorApp.Client.Desktop` into the new `MonitorApp.Client.Ui` library with an adaptive shell (side navigation on wide windows; bottom bar plus menu overlay below 720 px), card lists in place of data grids, and touch-sized controls. New sections: Devices home (peers with online state, last seen, headline metrics), Alerts (`GET /api/v1/alerts` on desktop, the received inbox on the phone), and phone pairing by typed address and code or pasted invitation. `MonitorApp.Client.Mobile.InProcessPeerDataSource` implements `IPeerDataSource` over `MobilePeerRuntime` (own and replicated data, push updates, viewing interest). `MonitorApp.Android` now hosts the Avalonia UI (adds the `Avalonia.Android` reference; lock file to be refreshed from CI). The unused DataGrid package was removed.
- Alerts are now pushed over held-open live sessions: once a live phone session has pulled alerts, the desktop wakes on each outbox enqueue (`AlertDeliveryService.WaitForPushAsync`) and sends an unsolicited `AlertBatch`; the phone's acknowledgement still follows its durable write and the outbox is unchanged (an unacknowledged batch is redelivered after 5 s). The phone's periodic pull on a live session is now a 30 s safety net (was 5 s). A loopback test asserts desktop alert to phone inbox under 2 s (about 0.2 s measured).
- Alert rules are debounced: threshold rules hold for `Sustained` (disk-free default now 5 min, was immediate), and a resolved rule/subject cannot re-fire until `AlertRulesConfig.RefireCooldown` (default 10 min) has passed. Defaults are working values recorded in T042.
- `GET /api/v1/alerts` now includes per-recipient `deliveries` (revision, enqueued/last-attempt time, attempts, `deliveredAt`). No user acknowledge or mute state exists yet, so none is reported.

- Held-open peer sessions are now live: after catch-up each side streams newly committed origin records (`PeerStore.Live` wakes a bounded in-flight sender; receivers acknowledge through the same idempotent per-origin replication, cursors and gaps stay authoritative, a gap acknowledgement rewinds the sender). The phone (`MobilePeerRuntime.Start`) keeps one long-lived session per paired desktop with capped-backoff reconnect instead of a connect-drain-close loop every ~15 s (`SyncOnceAsync` remains as a fallback); desktop `NodePeerConnectionManager` sessions also stream live and ask the remote to push its origin (the remote may have no locator). The server bounds live sessions by messages per minute (not a lifetime total), closes idle ones (`PeerHostOptions.LiveIdleTimeout`, 120 s) and ends them on host shutdown; stale acknowledgements no longer fail a session. gRPC keep-alive pings detect dead links.
- Peer node collection pacing is adaptive: `NodeCollectionScheduler` and the phone collection loop sample at the normal interval and switch to the fast interval (1 s) while any unexpired live interest exists (`AdaptiveSampler`, `LiveInterestRegistry`).
- Peer node now runs inside the .NET Generic Host (`PeerNodeHostedService`) with `UseWindowsService`/`UseSystemd` integration (systemd `Type=notify`, journald-friendly logs, graceful stop disposes the runtime, non-zero exit on startup failure; console run unchanged). Service mode defaults the data directory to `STATE_DIRECTORY`/`/var/lib/monitor-app` (Linux) or `%ProgramData%\MonitorApp` (Windows); `MONITOR_APP_DATA_DIR`, `MONITOR_APP_PEER_BIND`, `MONITOR_APP_PEER_PORT`, `MONITOR_APP_ADMIN_PORT` environment variables sit between arguments and defaults. Peer bind stays loopback unless set explicitly. Added Linux packaging (`eng/packaging/linux`: hardened systemd unit, sysusers, `/etc/monitor-app/node.conf`, DEB build script, RPM spec) and Windows service install/uninstall scripts (`eng/packaging/windows`). Adds `Microsoft.Extensions.Hosting.Systemd`/`.WindowsServices` 10.0.0.
- Added bounded history query (UTC window max 31 days, max 5000 rows, explicit truncation flag plus keyset cursor), as-of state reconstruction with age and freshness within a lookback, and a subject/signal catalog as `PeerHistoryQueryService` with versioned `/api/v1/history`, `/api/v1/state`, `/api/v1/catalog` endpoints that report a `resolution` (`raw` today) for later rollup tiers. Unavailable, denied, error, and undecodable observations are returned as states without values. SQLite schema version 3 adds an `observed_at` index. The loopback page gained minimal current-state, history, and as-of views and nonce-bound CSP/nosniff headers.
- Added the first shared client: `MonitorApp.Client.Core` (UI-free typed loopback-API client, `IPeerDataSource` abstraction, MVVM view models for Overview, Current state, History with line chart, As-of, and Pairing/trust) and `MonitorApp.Client.Desktop` (Avalonia 11.3 head with configurable node address). Current state updates by push when a source supports it and polls (5 s) otherwise. Tests drive the real `LocalApiHost` over SQLite; a headless Avalonia smoke test binds every view. The GUI has not been visually verified.
- Moved `IPeerAdvertisementProvider` and `PeerCapabilityRegistry` from Peer.Service to Peer.Replication (namespace unchanged) so Peer.Sync no longer references ASP.NET Core.
- Replaced the mandatory full-document preflight and default full-suite verification for every edit with a risk-based workflow: always inspect the index, todo, working tree, and governing decisions; read complete documents and run broad tests only when the change scope requires them.
- Expanded the documented product scope to a universal monitoring, inventory, and design model with an explicit boundary between actual/owned/running state and named plans. Added connector-and-length-centered cable management, physical/audio/RF/electrical/thermal constraints, sourcing and price history, deterministic automation and notifications, optional distributed local AI, and a dependency-ordered roadmap. ### Added

- Live protocol (additive `peer.proto`, fields 20-22): `LiveSubscribe`/`LiveSubscribeAck`, `LiveInterest` (subject, signals, lease seconds, 0 withdraws) and `LiveInterestAck`. Interest is accepted only from an authenticated, actively trusted peer, only for the receiver's own data, with a maximum lease (120 s), a bounded number of concurrent interests (16) and signals (32); revoking trust withdraws it.
- `PeerStore.Live` (`PeerLiveFeed`): in-process `Subscribe`/`IAsyncEnumerable` of newly committed local and replicated observations; `PeerNodeRuntime.LiveObservations`/`BeginViewing` and `MobilePeerRuntime.LiveObservations`/`BeginViewing` for UIs; loopback-only SSE endpoint `GET /api/v1/live` in `Peer.LocalApi` (same security headers; a connected viewer counts as live interest in the node's own data).
- Tests on real loopback gRPC and file-backed SQLite: two nodes streaming both ways without reconnect, phone and desktop streaming both ways, server killed mid-session then convergence without duplicates and live again, interest switching the real desktop scheduler to the fast interval and reverting on withdrawal, lease expiry and revocation, untrusted/revoked refusal, SSE emission, registry bounds, in-flight window and gap rewind.

- Physical-LAN self-observation: typed LAN entity/relationship kinds with validation in Contracts (`LanTopology`), and `MonitorApp.Peer.Collection.Lan` with a Linux (sysfs/procfs) and Windows (NetworkInformation) self-interface collector that classifies Tailscale/WireGuard/docker/bridge/loopback as non-physical, records link state, speed/duplex, MTU, own MAC (physical only), Wi-Fi vs Ethernet, VLAN sub-interfaces, own subnets and default-gateway IP, persists through existing PeerStore APIs (no schema change), and links per-peer segments only as inferred "probable same segment" edges. Unsupported platforms report truthful unsupported state. Not yet registered by the peer node.

### Security

- Alert delivery requires an authenticated, actively trusted PeerSession; a recipient receives only outbox rows addressed to its own peer id, a revoked or unpaired peer receives nothing and cannot acknowledge, acknowledgements cannot exceed an issued revision, and a phone rejects alerts whose origin is not the authenticated desktop. Alert text is bounded and carries rule and subject identifiers only, never credentials.
- Established initial trust boundaries and enrollment requirements before implementation.
- Replaced reusable raw agent credentials in enrollment responses with device public-key proof, SHA-256 fingerprints, and short-lived signed authentication challenges.
- Added structural rejection of malformed or wrong-curve public keys, incorrect secret/challenge/signature/fingerprint sizes, invalid challenge windows, and safe-error secret echo.
- Enrollment secrets are persisted only as per-record salted HMAC-SHA-256 verifiers with a required controller pepper; completion and device challenges are atomically single-use.
- Owner enrollment operations require an administrator token, and controller startup fails closed when bootstrap secrets are missing or weak.
- Update eligibility now fails closed for invalid signatures, untrusted keys, downgrade/reinstall, incompatible versions, wrong targets, and size/hash mismatch; signing and Android-keystore files are excluded from source control.
- Android enrollment retains the private P-256 key inside Android Keystore and never persists the one-time enrollment secret or proof challenge.
- Short pairing codes are one-time, 10-minute, never transmitted (PBKDF2-derived lookup id; the desktop reply carries an HMAC proof keyed by the code), globally rate-limited, and refuse unknown/expired/used/limited attempts identically; see `docs/SECURITY.md` Phone pairing.
