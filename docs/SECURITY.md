# Security and Privacy Model

## Scope and trust model

Monitor App is a decentralized personal monitoring mesh. There is no trusted Monitor App controller. Each peer protects its own identity key, local history, trust records, adapter credentials, and UI/API boundary.

Tailscale provides private reachability only. A Tailscale address, tailnet membership, LAN presence, hostname, or claimed device id never authenticates or authorizes a Monitor App peer. Pairing must be bilateral, prove possession of application keys, show the user the identity being trusted, and persist explicit pairwise trust. Reconnection uses that application identity with fresh replay-resistant authentication.

The first mesh is pairwise trust for personal scale. Transitive trust and global membership authority are out of scope. Revocation and key rotation must be explicit. Losing one peer must not silently revoke or authorize another.

## Peer transport and local storage

- Use authenticated encrypted transport even over Tailscale; verify peer application identity and fail closed on mismatch.
- Bind proof to the intended peer/session and fresh challenge. Limit message sizes, rates, buffers, and parallel work.
- Listen only on intentionally configured private/Tailscale interfaces, never public interfaces by default.
- Store private keys in platform-protected storage where available. Never transmit private keys or log pairing secrets, challenges, signatures, or reusable credentials.
- Service hosting: the Linux unit runs as the dedicated `monitor-app` user with `NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, an empty capability set, address families limited to AF_UNIX/AF_INET/AF_INET6/AF_NETLINK, and a 0700 state directory holding the 0600 identity file. The peer bind is loopback until `/etc/monitor-app/node.conf` sets an explicit address. Windows: DPAPI current-user scope binds the identity to `NT SERVICE\MonitorApp`, and the install script restricts the data directory ACL to that account, SYSTEM, and Administrators. Unverified: the unit under real systemd, SELinux policy, and all Windows behavior. ASP.NET data-protection keys land unencrypted under the state directory (`.aspnet`); they are not used for peer identity.
- Protect each peer's SQLite history, trust database, offline replication state, and backups with OS access controls. Diagnostics must be inspectable and redactable.
- Origin records retain immutable ids and sequence. Replication verifies origin identity, validates schemas/timestamps, is idempotent, and never grants control authority.

## Live sessions and interest

- Live push uses the existing signed per-origin records and authenticated session; there is no unsigned side channel. Every push re-checks active trust, and a revoked peer receives an error and the session ends.
- Live interest can only slow-to-fast the receiver's own sampling, only from an authenticated actively trusted peer, only for the receiver's own data, with a maximum lease, concurrent-interest and signal bounds (a peer cannot hold collection at 1 s indefinitely or flood it). Revoking trust withdraws that peer's interest. Fast sampling is a cost, not an authority grant.
- Held-open sessions are bounded by message rate, bounded in-flight batches, an idle timeout and heartbeat dead-peer detection. `GET /api/v1/live` is loopback-only with the same CSP/nosniff/no-store headers and read-only.

## Android peer

- The phone is outbound-only and opens no listener. Its P-256 identity key stays in Android Keystore and signs session and pairing proofs; the portable runtime only sees the `IPeerIdentityKey` abstraction.
- A pairing invitation carries address, peer id, and fingerprint only (no secret). Decoding enforces the private/loopback endpoint policy, 32-byte fingerprint, version, and size; it grants no trust. The phone pins the invitation fingerprint and the desktop user must explicitly approve.
- A remote refusal (revoked) is reported but does not alter phone-side trust, so an on-path attacker cannot silently revoke it. Foreground service starts only by explicit user action and shows a persistent notification. Android readings are battery/network state only; no communication identities are collected.

## Phone pairing (QR and typed code)

- Threat model: the invitation (QR/payload) carries only reachability and the desktop identity to pin; it is not a secret and grants no trust. The desktop user must still approve the phone's request after seeing its display name and fingerprint, so a leaked QR or code cannot add a device by itself.
- The advertised address is only the node's configured peer-listener address, never typed on the page or auto-bound; loopback/wildcard/public listeners are not advertised and the page explains the Tailscale/private-bind requirement.
- Typed code: 10 Crockford base32 characters (50 bits), 10-minute life, single-use, at most 8 live codes. The phone sends only a PBKDF2-SHA256 (100k iterations) derived lookup id, never the code, and the desktop reply (peer id, fingerprint) carries an HMAC keyed from the code, so a listener at the typed address that does not hold the code cannot substitute its own identity, and a passive observer cannot replay the exchange. Residual risk: an observer of the lookup id could brute-force 50 bits offline at 100k PBKDF2 iterations per guess (infeasible within the 10-minute life; the link is Tailscale/WireGuard-protected).
- Online guessing: every failed redemption counts against a global budget (8 per minute) after which all redemptions, including correct ones, are refused until the window passes. Unknown, expired, used, malformed, and rate-limited attempts return the identical status so the endpoint is not an oracle. This is a denial-of-service trade-off on a private, authenticated network.
- The invitation payload and code are rendered only on the loopback admin page (CSRF-protected generation, `no-store`, nonce CSP, inline SVG without scripts or style attributes).

- Alerts reach a phone only over its authenticated outbound PeerSession and only while its trust is Active; the outbox is keyed by recipient peer id, acknowledgements are bounded to issued revisions, and the phone accepts only alerts originated by the desktop it authenticated. Alert content is rule/subject identifiers and short operational text; a notification may be visible on the lock screen, so detail text must stay free of credentials and communication identities. Revocation during an already open session is not yet enforced for alert rows beyond the next request.

## Observed devices, adapters, and LAN infrastructure

Observed devices cannot authenticate as peers. A provisioned peer acts as collection gateway through a reviewed adapter. Every observation identifies the observed entity, collecting peer, adapter/module, source time, evidence, and quality.

Adapter and managed-switch credentials stay in the provisioned collector peer's protected local store and do not replicate. Collector ownership is explicit. Another peer may take over only after separate provisioning; automatic credential transfer or failover is prohibited. Prefer least-privilege, read-only accounts and isolate privileged collection where practical.

The T300 Cisco SG250 reader is separately provisioned and inactive until explicitly composed on a collector peer. It uses read-only SNMPv3 authPriv requests via locally installed Net-SNMP tools; passphrases live exclusively in a protected service-account `snmp.conf` directory and never appear in command arguments, serialized observation payloads or errors. The reader rejects public management IPv4 addresses, bounds query output and time, and never polls peers discovered from replicated topology. Credential directory ACLs, binary provenance, real switch authorization and node composition remain hardware/deployment verification obligations. The opt-in `Sg250CollectionPipeline` verifies enabled adapter instance plus explicit current collector ownership **before** contacting hardware. It refuses wrong-peer and unassigned collection, leaves topology unchanged on failed polls, and rejects conflicting strong bridge identity. These boundaries are tested against real SQLite without network hardware.

Topology evidence distinguishes reported facts from inference and carries source, time, quality, and confidence. Deduplicate switches with strong identity such as serial or chassis MAC, never IP alone.

LAN self-observation reads only the local peer's own interfaces (sysfs/procfs or OS interface APIs). It never reads ARP/neighbor tables, never collects gateway or other hosts' MACs, and never records flows or DNS. IP-derived claims (subnet, gateway IP) are weak and cannot establish identity or merge entities. The scheduled link observations (interface name, up/down, speed, duplex, MTU; never MAC addresses) are ordinary signed origin records and replicate to paired peers. Retention pin/unpin on the loopback API requires the same antiforgery token as other admin mutations. A replica accepts an origin-reported pruned range only from the stream's actively trusted owner and only when it starts no later than the next sequence the replica needs (T041).

## Collection breadth and privacy

“Anything that can be measured should be measured” means broad capability coverage with truthful categorization, not unlimited surveillance. Capability registration declares privacy class, cost, sampling/retention metadata, and required permissions. Secrets, authentication material, message/document contents, unrelated file contents, and unrelated payloads are excluded. Sensitive or high-cost categories require visible, explicit enablement.

Unsupported, denied, stale, and unavailable observations remain explicit; they must never be converted to zero. Raw detail stays local by default; replication uses declared summaries and budgets where appropriate.

## Network-data boundary

Ordinary monitoring may collect aggregate operational measurements without communication identities or content, including bandwidth/throughput, negotiated speeds, utilization, aggregate byte/packet totals, aggregate errors/drops/discards/retries/queue health, latency/reachability, and historical aggregate trends. Infrastructure facts such as interface/switch/port identity, link state, LLDP relationships explicitly reported by equipment, VLAN/admin configuration, PoE state/power, and management health are also allowed.

Ordinary monitoring must not collect packet captures, packet headers or payloads, individual packet records, flow/session/connection/socket logs, source/destination identities, DNS/query history, per-app/process traffic, content classification, or DPI. Module review and executable registration tests must reject prohibited observation declarations and permissions.

## Defensive security capability

Automated threat detection is a separate, explicitly enabled security capability. Baseline detection may use aggregate metrics, device identity/authentication failures, unexpected peer/config/link changes, unusual utilization, and existing summarized alerts from IDS, firewall, switch, or OS sources. Prefer summarized alerts over raw packets. Findings must preserve evidence, source, time, and confidence and must not claim compromise without support.

No default payload interception, credential/decryption collection, exploit attempt, indiscriminate scan, or monitoring outside networks the user owns or is authorized to monitor is allowed. Any deeper flow- or packet-derived security module requires separate permission, clear disclosure, explicit enablement, local processing, bounded retention, legal/authorization review, and additional security testing. Enabling it does not weaken the ordinary-monitoring prohibition.

## Remote monitoring control

Read-only telemetry and operational actions are different permission domains. The only remote commands are monitoring controls (pause/resume collection, sampling interval within 10 s-1 h, alert acknowledge and mute/unmute, pairing approve/reject); there is no power, service, script or file action.

- Every `ControlCommand` is signed by the issuer's identity key over an explicit canonical encoding binding issuer, target peer id, session id, issued/expires times (at most 2 minutes apart; 60 s by default; 30 s clock skew), a random nonce, the action and its payload. The desktop checks in order: issuer equals the authenticated session peer, target equals itself, session id equals the live session, trust is active (revoked and unknown peers are refused), signature, idempotent stored result, window, nonce and command-id reuse, payload bounds, per-peer grant, then user presence, then applies the effect. Results and nonces are persisted before the reply; a replayed identical command returns the stored result and changes nothing.
- Risk tiers: normal (resume, acknowledge, unmute, reject pairing, pause up to 1 h, mute up to 24 h, sampling interval), elevated (pause longer than 1 h or open-ended, mute longer than 24 h) and high (approve a pairing). Elevated and high commands need a second ECDSA P-256 signature from the issuer's registered user-presence key over the same canonical bytes under a different domain label. Grants cannot waive this.
- Presence key threat model: the key is separate from the identity key and, on Android, is a Keystore key with `setUserAuthenticationRequired(true)` and per-use strong-biometric authentication (timeout 0) used through BiometricPrompt with a CryptoObject, invalidated by the platform when fingerprints change. It defends against a compromised phone app or stolen identity key (identity-key access alone cannot approve a pairing or run a long pause), against a remote peer replaying captured commands (session binding, expiry, nonces), and against a malicious or buggy peer registering its own key: enrollment (`EnrollPresenceKey`, with a proof of possession) only creates a pending record; the desktop administrator must approve its fingerprint locally over the loopback API (CSRF protected), comparing it with the phone's displayed fingerprint. Not defended: a fully compromised desktop, an attacker holding the unlocked phone who can pass the biometric (the OS biometric policy applies), an attacker who can reach the desktop's loopback API as the local user, and software keys on devices without Keystore hardware (no key attestation yet).
- Authorization: grants are stored per trusted peer on the desktop (`control_grants`: monitoring controls, pairing approval, update approval). Absent a row the default is deny everything (owner decision 2026-11-22): a newly paired device can read replicated data but cannot pause, mute, change sampling, approve pairings or enroll a presence key until the administrator grants it locally. Pairing approval also always requires presence. A peer cannot decide its own pairing, and approval is refused when the request's fingerprint differs from what the phone showed. Pending-pairing summaries (name, fingerprint, expiry) are sent read-only to trusted peers that hold the pairing grant.
- Audit: every attempt (refused ones included, with a stable reason code, tier, session id and whether presence was verified) is appended to `control_audit`; database triggers reject UPDATE and DELETE. Local administrator decisions (grants, enrollment approval) are audited too. `GET /api/v1/audit` is loopback-only. Command payload details are summarized, never raw keys.
- Remote update approval (T044): `approve_update` installs only an update the node itself already downloaded, verified against the signed manifest and staged; the phone supplies no URL, file or version to fetch. It is high tier (presence signature required, never waivable), needs the separate `UpdateApproval` grant (default deny, so existing grants gain nothing), and carries the staged version plus artifact SHA-256 inside the signed (and presence-signed) canonical payload. The desktop refuses with `staged_update_changed` when its staged update differs, and the update agent re-checks version and digest atomically with starting the apply, so a newly staged release cannot be installed on a stale approval. Update status is readable only by an active trusted peer with the grant (others get `permitted=false` and no data); the status excludes URLs and paths. Reads and approvals are audited (`read_update_status`, `approve_update` with version and digest). Residual risk: a phone holding the grant and the unlocked biometric can install any validly signed staged release; a revoked or compromised signing key is outside this control.
- Manual overrides are in memory: a restart returns to normal monitoring. Muted alerts are held in the outbox, not dropped.

## Desktop-local user presence (T045)

High-risk local administration (approve a pairing, approve a phone's presence-key enrollment, grant control rights, approve an update install) needs a fresh proof that the interactive person is present once a desktop presence key is enrolled. Default policy is required-when-enrolled; `required` fails closed; `off` restores the old behavior.

- Flow: the node (a service without a desktop) issues a one-shot challenge bound to the action and subject; the desktop client verifies the person (Windows Hello, fprintd) and signs it with the enrolled key; the node verifies and consumes the challenge. Challenges live 60 s by default, are limited to 64 pending, and a captured proof cannot be replayed or reused for another pairing, update version or grant. Reject, revoke and lowering grants need no proof.
- Enrollment is trust on first use with proof of possession; a second key is refused; removal needs a proof from the enrolled key. The public key is kept in `local-presence.json` (0600); a corrupt file stops the node instead of disabling enforcement. Fingerprints and biometric data never leave the platform; the node stores only a public key.
- What it defends: a local process that can reach the loopback API and fetch a CSRF token but cannot drive the interactive person's Hello/fingerprint prompt or use the Windows Hello key, a browser-based attack on the local admin page, and an attacker with only a remote foothold. What it does not defend: local root/Administrator (can stop the node and delete the store or edit the database), and, on Linux, malware running as the same user (the software key is an owner-only file; fprintd gates the signature in the client process only). The first enrollment can be taken by a local process before the owner (trust on first use): it can lock the owner out of high-risk actions until they reset it with the node stopped, but it gains no new capability. The built-in admin web page cannot produce proofs.
- Windows Hello uses a hardware-backed `KeyCredential` (TPM when present) whose signature itself prompts Hello. Linux calls `fprintd-verify` with no arguments from a fixed absolute path that must not be group/world writable, without a shell, with a timeout that kills the process. Unverified on real Windows Hello and Fedora fprintd hardware.

## Action and update safety

The functional foundation is read-only. Future actions use a distinct permission domain; playful gestures never dispatch actions, historical mode cannot target live systems, material actions require preview/confirmation, commands expire, and results are audited.

Update manifests and artifacts remain signed and target/version/hash checked. Trusted release keys arrive through an authenticated installer or prior trusted release. Never introduce unsigned fallback, silent downgrade, or automatic overwrite as recovery.

Update pipeline trust: sources must be HTTPS but authenticity comes only from the signed manifest; downloads are size-capped and hash-verified into an owner-only staging directory and re-verified immediately before apply; apply requires explicit approval; a failed verification is never staged or applied; the highest seen version is persisted and a downgrade needs an audited per-version authorization; last-known-good is kept until the new version reports healthy; update state corruption fails closed; a crash during apply is reported as Failed. Android never installs silently and relies on the system installer. Node wiring: the unprivileged service only checks, verifies and stages; installation runs in a separate root helper that trusts only the signed manifest and the root-owned `/etc/monitor-app/update-key.json` (never the request file), copies the package to a root-owned directory before verifying its digest, and keeps the last-known-good package in a root-owned directory. A compromised service can at worst trigger the install of an already signed newer release. Default policy is approve-before-install (owner-confirmed); the local API approve endpoint is loopback-only with antiforgery. Signing material: the manifest key and Android keystore live only in the protected `release` environment; `eng/release/New-ReleaseSigningKeys.ps1` writes them outside the repository and never uploads. Possible future step-up: require the platform fingerprint/biometric prompt before approving an install. The health marker is local and unauthenticated, so it proves liveness only on a host the operator already controls.

Windows update apply boundary (T043): the node service runs as the virtual account `NT SERVICE\MonitorApp` with read/execute only on the install directory, so it cannot rewrite its own binaries and cannot replace itself while running. After the owner approves a staged update it writes `apply-request.json` (version and staged zip path) into its update directory and runs `schtasks /Run /TN MonitorAppUpdate`. That scheduled task is registered by the admin installer to run the node binary as SYSTEM with fixed arguments (`--apply-update <update dir> --install-root <root>`); only SYSTEM and Administrators can modify it, the service SID has read+execute only (it can start the task, nothing else), and the task has no triggers. The SYSTEM helper never trusts the request: it consumes it, requires the staged zip to lie inside the update directory, re-verifies the signed manifest against the admin-owned `update-key.json` shipped beside the helper binary, requires the manifest version to equal the approved version and be newer than the installed one, copies the zip to a SYSTEM-only work directory under the install root and verifies its SHA-256 on that private copy, then extracts side by side (zip-slip rejected), stops the service, repoints the `current` directory symlink, starts it, waits for a fresh health marker with the new version, and swaps back (and verifies the old version) on failure. The result file is created with `CreateNew`. Node-side approval is offered only when the admin-written `update-helper.json` marker exists in the install root; otherwise the node still downloads and verifies but never applies. Residual risks: the service can still trigger an apply of any already-signed, newer, staged release (bounded by anti-rollback and approval), it can delay or deny the update by tampering with the health marker or update directory, and the helper runs the currently installed (old) binary. Unverified on a real Windows host: task SDDL semantics, `schtasks /Run` from the service account, SCM starting a service whose binary path crosses a directory symlink, and ACL inheritance into SYSTEM-created version directories.

## Inventory, planning, and cable data

Actual inventory and running state are security-relevant facts. Design scenarios, candidate products, and proposed connections must not silently change actual state, collector configuration, automation inputs, or device controls. Promotion from design to actual is explicit and audited. Plan overlays must remain clearly labeled so an operator cannot mistake a proposed power, signal, network, or cable path for an installed one.

Cable records may expose work locations, equipment relationships, custody, and operational topology. Apply local access control, minimize exports, and keep optional labels free of secrets. The primary cable workflow uses manual templates and does not require QR codes or dedicated scanning hardware.

## External sourcing and notification egress

Product/source adapters and notification transports create outbound data flows. Each adapter declares destinations, fields sent, credentials, rate limits, retention, and third-party exposure. Store retailer/API credentials and notification tokens in protected local storage; never replicate or export them by default. Minimize notification text shown on lock screens and provide a privacy-safe mode.

Treat retailer pages, feeds, product specifications, URLs, labels, and imported notes as untrusted data. Sanitize stored/displayed content, bound fetches and parsing, resist server-side request forgery, and never let source text choose tools, destinations, credentials, or actions. Respect provider terms and access restrictions. A retrieval failure is unavailable evidence, not price zero or out of stock.

Automation requires a durable execution owner and idempotency boundary so replicated events cannot duplicate notifications or actions. Rule changes, ownership transfer, destinations, and permission changes are audited. Notification permission never implies operational-control permission.

## Local AI safety

Models, prompts, retrieved text, embeddings, and generated output are untrusted. AI receives explicit task and tool grants and the minimum actual/design context required. Tool validation and authorization occur outside the model. Prompt or retrieved text cannot expand permissions, reveal credentials, alter peer trust, or bypass confirmation.

Generated facts and recommendations retain model/runtime version and source references and do not overwrite observed or user-confirmed facts. AI does not own replication, automation schedules, notification delivery, identity, or trust. Material actions use the ordinary permission, preview, confirmation, expiration, idempotency, and audit path regardless of who proposed them.

## Required security tests

- Tailnet/LAN membership without a paired application identity fails.
- Wrong key, peer substitution, replay, expired challenge, and revoked peer fail closed without secret leakage.
- Replication rejects altered origin identity, conflicting duplicate sequence, incompatible schema, and unauthorized stream requests.
- Capability registration rejects prohibited network-data categories and undeclared elevated permissions.
- Adapter credentials never appear in replicated records, logs, exports, or module descriptors.
- Collector failover cannot occur until the second peer is explicitly provisioned.
- Security findings require evidence/confidence; deeper security modules cannot start without their separate enablement and retention policy.
- Tampered or incorrectly targeted update manifests/artifacts fail closed.
- Design-only objects and relationships cannot be consumed as actual state without an explicit transition.
- Source and notification adapters protect credentials, restrict egress, redact diagnostics, and reject untrusted destinations and oversized/malicious input.
- Replicated automation inputs produce at most one owned action and cannot bypass action permissions.
- AI and retrieved content cannot expand tool grants, modify authoritative facts silently, expose secrets, or dispatch material actions without the ordinary approval path.

## Current peer-foundation evidence

On Linux the preview node has no DPAPI equivalent. Its P-256 identity key is a PKCS#8 file `identity.p256` in a 0700 data directory, created atomically at 0600 (temp file then no-overwrite rename), and the node refuses to load it if it is group/other accessible, a symlink, or owned by another user. This protects against other local users, not against root or the same user; keyring/TPM-backed storage is deferred. Linux evidence is an Ubuntu 24.04 container only.

The peer libraries now validate P-256 SPKI structure and SHA-256 fingerprints, bind bilateral fresh-pairing and reconnect proofs to both identities and the full session/challenge transcript, enforce fixed P1363 signatures and expiry, durably reject replay across restart, negotiate explicit compatibility, and persist trust/revocation and immutable origin records in SQLite WAL. Fresh pairing requires an initiating user action plus explicit approval on the contacted peer; pairing IDs are identity-bound and idempotent, and neither side stores trust before proof and completed confirmation. Origin replication verifies source trust, content hashes, signatures, bounds, conflicts, and durable cursors. Inbound/outbound transport fails closed on unsafe endpoints and requires protocol 1.1 bilateral proof. The administration surface is loopback-only with CSRF-protected mutations. The Windows preview stores its private identity key under CurrentUser DPAPI, keeps reconnect locators separate from application identity, and signs collected system observations before persistence. Credential references are omitted from replication descriptors and capability declarations cannot carry credential/private-key fields. Observed-device assignment validates that the selected local adapter names the same entity and collector peer; reassignment history is retained, adapter credential references remain local, and an IP/network address is rejected as strong identity. The Yamaha spike runs a fixed, non-interactive read-only PnP query with no user-provided script or credential input, a bounded timeout, safe reason codes, and no control path. Capability registration rejects prohibited ordinary network categories before persistence; defensive-security declarations require separate enablement, defensive privacy classification, evidence, confidence, and positive retention metadata. A real Windows loopback test proves separate-store reconnect and signed history convergence after offline collection. Real TLS/Tailscale deployment, non-Windows protected key stores, connection/rate limiting beyond per-session bounds, revocation during an established live session, and the remaining network-attack matrix remain unverified.
